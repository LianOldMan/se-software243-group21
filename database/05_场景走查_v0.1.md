## 1. 走查范围与方法

按指导书要求，每个场景记录“给定数据 — 操作 — 预期变化 — 约束依据”，并在最后列出可检查的一致性断言。

- 物理表以 `03_逻辑表设计与数据字典_v0.1.md` 为准：`user_account`、`book_listing`、`reservation_order`。
- 主键：`user_account.user_id`、`book_listing.listing_id`、`reservation_order.order_id`。
- 外键：`book_listing.seller_id → user_account.user_id`；`reservation_order.buyer_id → user_account.user_id`；`reservation_order.listing_id → book_listing.listing_id`。
- 技术派生：`reservation_order.active_listing_id`（生成列，`CASE WHEN order_status='有效' THEN listing_id ELSE NULL END`）+ UNIQUE。
- 幂等：`reservation_order.request_token` + `UNIQUE(buyer_id, request_token)`。

## 2. 场景 S1：正常预留（对应 UC-04、FR-05/06）

### 给定数据

| 表 | 记录 |
|---|---|
| `user_account` | U1（`user_id=1`，卖家）、U2（`user_id=2`，买家，U2 ≠ U1） |
| `book_listing` | L1（`listing_id=101`，`seller_id=1`，`availability_status='可售'`） |
| `reservation_order` | 空 |

### 操作

U2 对 L1 发起预留，携带 `request_token='r1'`；服务在一个事务内完成：锁定 L1 行 → 校验状态 → 校验 U2 ≠ seller → 插入订单 → 更新 L1 状态。

### 预期变化

| 表 | 变化 |
|---|---|
| `reservation_order` | 新增 O1（`order_id=5001` 自增）：`listing_id=101`、`buyer_id=2`、`order_status='有效'`、`placed_at=提交时刻`、`cancelled_at=NULL`、`request_token='r1'`、`active_listing_id=101`（生成列） |
| `book_listing` | L1：`availability_status` 由“可售”变为“已预留”，其余字段不变 |

### 约束依据

| 约束 | 由谁保证 |
|---|---|
| `buyer_id=2` 的账号存在 | FK `reservation_order.buyer_id → user_account.user_id` |
| `listing_id=101` 的书籍存在 | FK `reservation_order.listing_id → book_listing.listing_id` |
| 同书有效订单至多一条 | UNIQUE(`active_listing_id`)，本例仅一条，无冲突 |
| 禁止自购（R-04） | **事务内**读取 `book_listing.seller_id` 与 `buyer_id` 比较，FK/CHECK 无法表达 |
| 书籍状态与订单状态一致 | **同一事务**内两次写入，提交前复核 |

### 可检查断言（设计预期）

1. `SELECT COUNT(*) FROM reservation_order WHERE listing_id=101 AND order_status='有效'` → 1
2. `SELECT availability_status FROM book_listing WHERE listing_id=101` → `已预留`
3. `SELECT COUNT(*) FROM reservation_order o JOIN book_listing b ON o.listing_id=b.listing_id WHERE o.buyer_id=b.seller_id` → 0（无自购记录）

## 3. 场景 S2：取消后再次预留 + 旧请求重放（对应 UC-05、FR-07/08、B-05）

### 给定数据

| 表 | 记录 |
|---|---|
| `reservation_order` | O1（`order_id=5001`、`listing_id=101`、`buyer_id=2`、`order_status='有效'`、`active_listing_id=101`、`cancelled_at=NULL`） |
| `book_listing` | L1（`listing_id=101`、`seller_id=1`、`availability_status='已预留'`） |
| `user_account` | U3（`user_id=3`，非 L1 卖家） |

### 操作与预期变化

**操作 1：U2 取消 O1**（请求按具体 `order_id=5001` 定位，携带当前用户 `user_id=2`）

| 表 | 预期变化 |
|---|---|
| `reservation_order` | O1：`order_status` 由“有效”改为“已取消”；`cancelled_at` 写入提交时刻；`active_listing_id` 派生为 NULL；行**保留**，不删除 |
| `book_listing` | L1：确认无其他有效订单后，`availability_status` 由“已预留”恢复为“可售” |

**操作 2：U3 再次预留 L1（`request_token='r2'`）**

| 表 | 预期变化 |
|---|---|
| `reservation_order` | 新增 O2（`order_id=5002`）：`listing_id=101`、`buyer_id=3`、`order_status='有效'`、`active_listing_id=101` |
| `book_listing` | L1：`已预留` |

**操作 3：U2 重放旧的取消请求（仍指向 `order_id=5001`）**

| 表 | 预期变化 |
|---|---|
| `reservation_order` | 无变化：O1 已“已取消”，定位到 O1 后状态校验不通过，影响行数为 0（返回“订单已取消或无效”） |
| `book_listing` | 无变化：**不得**因旧请求把 L1 从“已预留”释放为“可售” |
| `reservation_order` | O2 保持“有效”，不得被取消 |

### 约束依据

| 约束 | 由谁保证 |
|---|---|
| 旧订单与新订单不混淆 | 主键 `order_id` 定位，取消请求必须携带 `order_id`，**禁止**按 `listing_id` 批量取消 |
| 只有买家本人能取消 | SQL 条件 `WHERE order_id=? AND buyer_id=? AND order_status='有效'`，影响行数为 0 即拒绝 |
| 旧 O1 不干扰新 O2 | 状态校验 + 事务隔离；O1 的 `active_listing_id` 已为 NULL，不占用唯一索引 |
| 历史保留 | 只改 `order_status`/`cancelled_at`，不执行 DELETE |
| 书籍状态与有效订单数一致 | 取消事务内先锁 L1，确认“无其他有效订单”后才恢复可售 |

### 可检查断言（设计预期）

1. `SELECT order_status, cancelled_at, active_listing_id FROM reservation_order WHERE order_id=5001` → `已取消`、非 NULL、NULL
2. `SELECT order_status FROM reservation_order WHERE order_id=5002` → `有效`
3. `SELECT availability_status FROM book_listing WHERE listing_id=101` → `已预留`（重放旧请求后仍不变）
4. 所有 `order_status='已取消'` 的行：`cancelled_at IS NOT NULL`；所有有效行：`cancelled_at IS NULL`

## 4. 场景 S3：并发竞争与回包丢失重试（对应 UC-04 A5、NFR-02）

### 4.1 S3-A 同书竞争

**给定**：L1 可售（`seller_id=1`）；U2、U3 均非卖家；两人几乎同时发起预留（token 分别为 `r2`、`r3`）。

**操作**：两个事务都先 `SELECT ... FOR UPDATE` 锁定 L1 行。

**预期变化**：

| 情形 | 结果 |
|---|---|
| T1 先获得行锁 | T1 读到“可售”且无有效订单 → 插入 O_a、置 L1“已预留” → 提交 |
| T2 等待后读到 | L1 已是“已预留” → 拒绝，**不插入**订单，返回“该书已被预留” |
| 两人都通过检查（极端情况） | 唯一索引 `active_listing_id` 冲突，后提交事务回滚，至多一条有效订单 |

**约束依据**：行锁保证检查与写入的原子性；`UNIQUE(active_listing_id)` 作为兜底；失败方只能得到“已被预留”，**不得**获得对方 `buyer_id`、订单号等信息。

**断言**：`SELECT COUNT(*) FROM reservation_order WHERE listing_id=101 AND order_status='有效'` → 1；`SELECT COUNT(*) FROM reservation_order WHERE listing_id=101 AND order_status='已取消'` 不受影响（可为 0）。

### 4.2 S3-B 回包丢失后的幂等重试

**给定**：U2 携带 `request_token='r1'` 请求预留 L1，事务已提交（O1 生成、L1 已预留），但响应在网络上丢失。

**操作**：U2 客户端以**同一** `request_token='r1'` 重试。

**预期变化**：

| 表 | 结果 |
|---|---|
| `reservation_order` | 唯一键 `(buyer_id=2, request_token='r1')` 冲突 → 服务**查询并返回原订单 O1**，不新建记录 |
| `book_listing` | 保持“已预留” |

**约束依据**：`UNIQUE(buyer_id, request_token)`；服务在唯一冲突时按“查询原结果”处理，而不是返回失败或重新下单。

**断言**：`SELECT COUNT(*) FROM reservation_order WHERE buyer_id=2 AND request_token='r1'` → 1；整表有效订单数不变。

> 说明：若客户端**换了** token 重复下单，数据库唯一键无法拦截，此时由“L1 已非可售”这一状态检查拒绝，返回“该书已被预留”。

## 5. 跨表约束的实现责任划分

| 约束 / 规则 | FK、CHECK、UNIQUE 能否保证 | 实际责任方 | 依据 |
|---|---|---|---|
| 订单的书籍、买家必须存在 | ✅ FK 可保证 | 数据库 | 三个 FK 均 NOT NULL |
| 每条书籍必须有卖家 | ✅ FK 可保证 | 数据库 | `seller_id` NOT NULL |
| 同一本书至多一条有效订单 | ✅ 生成列 UNIQUE 可保证 | 数据库 | `active_listing_id` |
| 同一逻辑下单请求不重复建单 | ✅ UNIQUE(buyer_id, request_token) | 数据库 + 服务 | 冲突时返回原单 |
| 禁止自购（R-04） | ❌ 跨表身份比较 | **应用/事务** | 读 `seller_id` 与 `buyer_id` 比对 |
| 只有买家本人能取消 | ❌ 行级权限 | **应用/事务** | `WHERE order_id=? AND buyer_id=?` |
| 旧 O1 请求不影响新 O2 | ❌ 需要状态判断 | **应用/事务** | 按 `order_id` 定位 + 状态校验 |
| 书籍状态与有效订单数一致 | ❌ 跨表等价关系 | **同一事务** | 提交前复核 `可售 ⇔ 0 条有效`、`已预留 ⇔ 1 条有效` |
| 不泄露他人订单 | ❌ | **查询条件与响应过滤** | 失败响应不含对方标识 |
| 价格两位小数（R-03） | ⚠️ `DECIMAL(10,2)` 可能隐式舍入 | **应用输入校验** | 写入前按字符串拒绝 12.345 |

| 编号 | 断言 | 预期 |

| A-1 | `book_listing.availability_status='已预留'` 的每本书，存在且仅存在一条有效订单 | 不满足为 0 行 |
