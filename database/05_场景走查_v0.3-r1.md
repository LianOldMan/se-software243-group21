## 1. 走查范围与技术前提

按指导书要求，每个场景记录“给定数据 — 操作 — 预期变化 — 约束依据”，并在第 6 节列出可检查的一致性断言。

### 1.1 物理对象（以数据字典 v0.3 为准）

- 表：`user_account`、`book_listing`、`reservation_order`。
- 主键：`user_account.user_id`、`book_listing.listing_id`、`reservation_order.order_id`。
- 外键（三条，均 `NOT NULL`，建议 `ON DELETE RESTRICT`）：
  - `book_listing.seller_id → user_account.user_id`
  - `reservation_order.buyer_id → user_account.user_id`
  - `reservation_order.listing_id → book_listing.listing_id`
- 技术派生列：`reservation_order.active_listing_id`，定义为
  `CASE WHEN order_status='有效' THEN listing_id ELSE NULL END`，加 `UNIQUE`。
  **它是本行的派生技术列，不是实体、不是外键**；作用是让“同书有效订单 ≤ 1”由数据库强制。
- 幂等列：`reservation_order.request_token CHAR(36) NOT NULL`，配 `UNIQUE(buyer_id, request_token)`。本参考实现的接口协议规定由**服务端在首次下单请求发送之前签发并交给客户端持有** 36 字符规范 UUID；同动作重试必须复用、跨书复用必须拒绝。数据库 CHAR(36) 本身**不校验 UUID 格式**。
  本 MySQL 参考设计**保留必填** `request_token`（A 在 #9 已确认该技术选择）。

### 1.2 方言与模式前提（结论成立的条件）

| 前提 | 说明 |
|---|---|
| MySQL **≥ 8.0.16**（参考运行前提） | 本项目统一以 MySQL ≥ 8.0.16 为参考运行前提：`CHECK` 约束**自 8.0.16 起才真正执行**（5.7 会解析但忽略）；`GENERATED ALWAYS AS ... STORED` 生成列**自 MySQL 5.7 起已支持**，本设计只是统一放在 8.0.16+ 下定义与验证，并非生成列从 8.0.16 才开始有 |
| `sql_mode` 含 `STRICT_TRANS_TABLES` | 否则超长/非法值可能被静默截断，`price`、`account_code` 等长度与取值范围失去防护 |
| `DECIMAL(10,2)` 不等于精度校验 | MySQL 对 `12.345` 会按列定义舍入为 `12.35` 并可能只给 Note；R-03“最多两位小数、不四舍五入”必须由应用在写入前按**字符串**判定，见 5 节责任表 |
| 未执行任何 DDL/DML | 本文所有结论均为设计推演；“唯一冲突会回滚”“行锁会阻塞”等属于 InnoDB 语义推论，非实测 |

## 2. 场景 S1：正常预留（对应 UC-04、FR-05/06）

### 给定数据

| 表 | 记录 |
|---|---|
| `user_account` | U1（`user_id=1`，卖家）、U2（`user_id=2`，买家，U2 ≠ U1） |
| `book_listing` | L1（`listing_id=101`，`seller_id=1`，`availability_status='可售'`） |
| `reservation_order` | 空 |

### 操作

U2 对 L1 发起预留，携带 `request_token='11111111-1111-4111-8111-111111111111'`（教学用的 36 字符规范 UUID 示例；真实运行每次动作由服务端随机签发、客户端重试复用，不固定使用此示例值）；服务在一个事务内完成：锁定 L1 行 → 校验状态 → 校验 U2 ≠ seller → 插入订单 → 更新 L1 状态。

### 预期变化

| 表 | 变化 |
|---|---|
| `reservation_order` | 新增 O1（`order_id=5001` 自增）：`listing_id=101`、`buyer_id=2`、`order_status='有效'`、`placed_at=提交时刻`、`cancelled_at=NULL`、`request_token='11111111-1111-4111-8111-111111111111'`、`active_listing_id=101`（生成列） |
| `book_listing` | L1：`availability_status` 由“可售”变为“已预留”，其余字段不变 |

### 约束依据

| 约束 | 由谁保证 |
|---|---|
| `buyer_id=2` 的账号存在 | FK `reservation_order.buyer_id → user_account.user_id` |
| `listing_id=101` 的书籍存在 | FK `reservation_order.listing_id → book_listing.listing_id` |
| 同书有效订单至多一条 | UNIQUE(`active_listing_id`)，本例仅一条，无冲突 |
| 禁止自购（R-04） | **事务内**读取 `book_listing.seller_id` 与 `buyer_id` 比较，FK/CHECK 无法表达 |
| 书籍状态与订单状态一致 | **同一事务**内两次写入，提交前复核 |

### 可检查断言（设计预期，提交后）

1. `SELECT COUNT(*) FROM reservation_order WHERE listing_id=101 AND order_status='有效'` → 1
2. `SELECT availability_status FROM book_listing WHERE listing_id=101` → `已预留`
3. `SELECT COUNT(*) FROM reservation_order o JOIN book_listing b ON o.listing_id=b.listing_id WHERE o.buyer_id=b.seller_id` → 0（无自购记录）
4. O1 的 `cancelled_at IS NULL`，且 `placed_at` 不晚于当前时间

## 3. 场景 S2：取消后再次预留 + 旧请求重放（对应 UC-05、FR-07/08、B-05）

### 给定数据

| 表 | 记录 |
|---|---|
| `reservation_order` | O1（`order_id=5001`、`listing_id=101`、`buyer_id=2`、`order_status='有效'`、`active_listing_id=101`、`placed_at=2026-11-17 10:00:00`、`cancelled_at=NULL`） |
| `book_listing` | L1（`listing_id=101`、`seller_id=1`、`availability_status='已预留'`） |
| `user_account` | U3（`user_id=3`，非 L1 卖家） |

### 操作与预期变化

**操作 1：U2 取消 O1**（请求按具体 `order_id=5001` 定位，携带当前用户 `user_id=2`）

| 表 | 预期变化 |
|---|---|
| `reservation_order` | O1：`order_status` 由“有效”改为“已取消”；`cancelled_at` 写入提交时刻（**必须 ≥ `placed_at`=2026-11-17 10:00:00**）；`active_listing_id` 派生为 NULL；行**保留**，不删除 |
| `book_listing` | L1：确认无其他有效订单后，`availability_status` 由“已预留”恢复为“可售” |

**操作 2：U3 再次预留 L1（`request_token='22222222-2222-4222-8222-222222222222'`）**

| 表 | 预期变化 |
|---|---|
| `reservation_order` | 新增 O2（`order_id=5002`）：`listing_id=101`、`buyer_id=3`、`order_status='有效'`、`active_listing_id=101` |
| `book_listing` | L1：`已预留` |

**操作 3：U2 重放旧的取消请求（仍指向 `order_id=5001`）**

| 表 | 预期变化 |
|---|---|
| `reservation_order` | 无变化：O1 已“已取消”，定位到 O1 后状态校验不通过，影响行数为 0（返回“订单已取消或无效”） |
| `book_listing` | 无变化：**不得**因旧请求把 L1 从“已预留”释放为“可售” |
| `reservation_order` | O2 保持“有效”，不得被取消 |

### 约束依据

| 约束 | 由谁保证 |
|---|---|
| 旧订单与新订单不混淆 | 主键 `order_id` 定位，取消请求必须携带 `order_id`，**禁止**按 `listing_id` 批量取消 |
| 只有买家本人能取消 | SQL 条件 `WHERE order_id=? AND buyer_id=? AND order_status='有效'`，影响行数为 0 即拒绝 |
| 旧 O1 不干扰新 O2 | 状态校验 + 事务隔离；O1 的 `active_listing_id` 已为 NULL，不占用唯一索引 |
| 历史保留 | 只改 `order_status`/`cancelled_at`，不执行 DELETE |
| **取消时间不得早于下单时间** | 应用在写入 `cancelled_at = NOW()` 时以行内 `placed_at` 为下界；断言 A-7 检查 `cancelled_at >= placed_at`。数据库层也可写成 `CHECK (cancelled_at IS NULL OR cancelled_at >= placed_at)`，但该 CHECK **需 MySQL 8.0.16+ 才真正执行**（门槛见 1.2） |
| 书籍状态与有效订单数一致 | 取消事务内先锁 L1，确认“无其他有效订单”后才恢复可售 |

### 可检查断言（设计预期，提交后）

1. `SELECT order_status, cancelled_at, active_listing_id FROM reservation_order WHERE order_id=5001` → `已取消`、非 NULL、NULL
2. `SELECT order_status FROM reservation_order WHERE order_id=5002` → `有效`
3. `SELECT availability_status FROM book_listing WHERE listing_id=101` → `已预留`（重放旧请求后仍不变）
4. 所有 `order_status='已取消'` 的行：`cancelled_at IS NOT NULL`；所有有效行：`cancelled_at IS NULL`
5. `SELECT COUNT(*) FROM reservation_order WHERE cancelled_at IS NOT NULL AND cancelled_at < placed_at` → 0（**新增**：取消时间不早于下单时间）

## 4. 场景 S3：并发竞争与回包丢失重试（对应 UC-04 A5、NFR-02）

### 4.1 S3-A 同书竞争

**给定**：L1 可售（`seller_id=1`）；U2、U3 均非卖家；两人几乎同时发起预留（token 分别为 `33333333-3333-4333-8333-333333333333`、`44444444-4444-4444-8444-444444444444`）。

**操作**：两个事务都先 `SELECT ... FOR UPDATE` 锁定 L1 行。

**预期变化**：

| 情形 | 结果 |
|---|---|
| T1 先获得行锁 | T1 读到“可售”且无有效订单 → 插入 O_a、置 L1“已预留” → 提交 |
| T2 等待后读到 | L1 已是“已预留” → 拒绝，**不插入**订单，返回“该书已被预留” |
| **若实际实现存在缺陷，未按上述统一锁协议检查**（不是上述正确加锁流程的正常分支） | 即使错误地让两个请求都尝试写有效订单，生成列 `active_listing_id` + UNIQUE 仍可作为最后一道防线，使其中一个 INSERT/事务因唯一冲突失败并回滚；服务应安全结束或重试整个事务 |

**约束依据**：行锁保证检查与写入的原子性；`UNIQUE(active_listing_id)` 作为兜底；失败方只能得到“已被预留”，**不得**获得对方 `buyer_id`、订单号等信息。

**断言**：`SELECT COUNT(*) FROM reservation_order WHERE listing_id=101 AND order_status='有效'` → 1。

### 4.2 S3-B 回包丢失后的幂等重试（含跨书籍 token 复用）

**情形 B-1：同一本书、同一 token 重试（正常幂等）**

**给定**：U2 携带 `request_token='11111111-1111-4111-8111-111111111111'` 请求预留 L1，事务已提交（O1 生成、L1 已预留），但响应在网络上丢失。

**操作**：U2 客户端以**同一** `request_token='11111111-1111-4111-8111-111111111111'`、**同一** `listing_id=101` 重试。

**预期变化**：

| 表 | 结果 |
|---|---|
| `reservation_order` | 唯一键 `(buyer_id=2, request_token='11111111-1111-4111-8111-111111111111')` 冲突后，**先回滚失败的写入事务，再在新事务/可用会话中按买家与 token 查询并比对 listing_id**；同目标则返回 O1 的真实现有结果，不新建记录 |
| `book_listing` | 保持“已预留” |

**约束依据**：`UNIQUE(buyer_id, request_token)`；服务在唯一冲突时按“查询原结果”处理，而不是返回失败或重新下单。

**断言**：`SELECT COUNT(*) FROM reservation_order WHERE buyer_id=2 AND request_token='11111111-1111-4111-8111-111111111111'` → 1；整表有效订单数不变。

**情形 B-2：跨书籍复用同一 token（必须拒绝，不得张冠李戴）**

**给定**：O1 已存在（`buyer_id=2`、`request_token='11111111-1111-4111-8111-111111111111'`、`listing_id=101`、`order_status='有效'`）；另有 L2（`listing_id=102`，可售，`seller_id=1`）。

**操作**：U2 用**同一** `request_token='11111111-1111-4111-8111-111111111111'` 去预留 **L2**（`listing_id=102`）。

**预期变化**：

| 表 | 结果 |
|---|---|
| `reservation_order` | 唯一键 `(buyer_id=2, request_token='11111111-1111-4111-8111-111111111111')` 冲突。服务读取原记录后发现 `listing_id=101 ≠ 102` → **返回冲突/拒绝（如“request_token 已被用于其他书籍的下单请求”）**，**不新建记录**，**也不得返回 O1 作为 L2 的成功结果** |
| `book_listing` | L2 保持“可售”；L1 保持“已预留” |

**约束依据**：

- `UNIQUE(buyer_id, request_token)` 只能保证“同一买家同一 token 最多一行”，它**无法区分**这行是给哪本书的——因此**跨书籍复用必须由服务层判定**：冲突时先按 `(buyer_id, request_token)` 查出原记录，比较 `listing_id`；相同则幂等返回，不同则拒绝。
- 若把幂等键直接写成 `(buyer_id, request_token, listing_id)` 或允许复合键区分书籍，等于**放弃**“请求级幂等”，A 已确认不采用；因此拒绝逻辑必须显式写在服务层。
- 该情形属于客户端违约（token 应每笔请求唯一），数据库唯一键本身不能判定“同一 token 换了一本书”的业务语义，因此采用**服务层判定 + 数据库唯一键兜底**；本章不排除将来其他等价设计。

**断言**：

1. `SELECT listing_id FROM reservation_order WHERE buyer_id=2 AND request_token='11111111-1111-4111-8111-111111111111'` → 仍只有 `101`
2. `SELECT COUNT(*) FROM reservation_order WHERE listing_id=102` → 0
3. `SELECT availability_status FROM book_listing WHERE listing_id=102` → `可售`

> 说明：若客户端**换了** token 重复下单同一本书，唯一键无法拦截，此时由“L1 已非可售”这一状态检查拒绝，返回“该书已被预留”。

### 4.3 S4：卖家自购拒绝（R-04；负向设计推演）

**给定数据**：L1 由 U1 发布（`seller_id=1`），状态“可售”；U1 试图以 `buyer_id=1` 预留 L1，携带新的 36 字符 UUID。

**操作**：事务中先锁 L1，服务验证买家账号与书籍的发布者，发现 `buyer_id = seller_id`，拒绝创建订单；不修改书籍状态。

**预期变化**：订单数不增加；L1 仍“可售”。**依据**：R-04/FR-05、UC-04 A4，跨表身份校验必须由业务服务实现，三个普通外键并不禁止自购；若有未来实测，A-3 应返回零条异常记录。

### 4.4 S5：非订单买家越权取消（FR-08；负向设计推演）

**给定数据**：L1 当前已预留；O1（`order_id=5001`，买家 U2）有效；U3 发起取消 O1。

**操作**：按书籍行锁顺序取得 L1 后，按 `order_id=5001 AND buyer_id=3 AND order_status='有效'` 检查/条件更新订单；不满足归属返回 0 行。

**预期变化**：O1 仍有效、L1 仍“已预留”，未产生其他订单，也不泄露 U2 身份。**依据**：FR-08/UC-05，仅订单本人可取消，必须核验实际 `buyer_id`，不能只靠 FK 或只按 `listing_id` 取消。

### 4.5 S6：发布价格边界（R-03；输入层负向设计推演）

| 给定价格原始输入 | 操作 | 预期变化 | 依据 |
|---|---|---|---|
| `0` | 提交发布 | 拒绝，不新增 book_listing | R-03：价格必须 >0；`CHECK(price > 0)` 也可兜底，但先在应用层反馈 |
| `-5` | 提交发布 | 拒绝，不新增 book_listing | R-03、同上 |
| `12.345` | 提交发布 | **必须在转为 DECIMAL(10,2) 前拒绝**，不得自动写成 12.35 | R-03、UC-01 AC-01-4；数据库可能舍入，必须校验原始字符串精度 |
| `12.34` | 提交其他字段均有效的发布 | 可新增一条“可售”记录，发布时间由系统生成 | R-01/R-03、FR-01 |

**说明**：四个输入只是设计案例，不是已经在数据库实测通过。

### 4.6 S7：同一订单两次并发取消（FR-07/08、AC-05-5；设计推演）

**给定数据**：L1“已预留”，O1（`order_id=5001`，`buyer_id=2`）状态有效。U2 的两个取消请求 T1/T2 几乎同时抵达。

**操作**：两事务均按**先锁 book_listing(L1)、再检查订单 O1**的相同锁顺序执行。T1 先获得锁，校验归属/有效后在同一事务将 O1 改为“已取消”、写入 `cancelled_at >= placed_at` 并让 L1“可售”；T2 等待后再次检查 O1，发现已取消，拒绝重复取消。

**预期变化**：仅 T1 可以发生一次有效→已取消转换，O1 历史保留，L1 最终“可售”；T2 不得再次释放或覆盖随后可能的新有效订单。**依据**：订单主键 + 状态条件更新 + 统一行锁顺序 + 同一事务，不能只按书籍编号去取消订单。若是异常系统未按约定加锁，应依赖行状态条件与重试防止额外更新。

### 4.7 订单创建时间不可由请求指定（第25组外评必改 M2；计划负向验收）

**给定**：用户试图在发布/下单请求体中额外提供 `published_at='2000-01-01'` 或 `placed_at='2000-01-01'`。

**预期**：服务端字段白名单应拒绝或忽略非授权时间字段，创建记录时省略这两列，由 `DEFAULT CURRENT_TIMESTAMP(6)` 填写；后续普通状态变更不可修改创建时间。

**技术边界**：本参考 SQL 的 DEFAULT **不能阻止高权限直接 INSERT/UPDATE 时间列**；此为待设计/待实测的接口要求，而非数据库已经强制保障。未来如要 DB 级强制，需列级权限/触发器等额外措施。

## 5. 跨表约束的实现责任划分

| 约束 / 规则 | FK、CHECK、UNIQUE 能否保证 | 实际责任方 | 依据 |
|---|---|---|---|
| 订单的书籍、买家必须存在 | ✅ FK 可保证 | 数据库 | 三个 FK 均 NOT NULL |
| 每条书籍必须有卖家 | ✅ FK 可保证 | 数据库 | `seller_id` NOT NULL |
| 同一本书至多一条有效订单 | ✅ 生成列 UNIQUE 可保证 | 数据库 | `active_listing_id` |
| 同一逻辑下单请求不重复建单 | ✅ UNIQUE(buyer_id, request_token) | 数据库 + 服务 | 冲突时返回原单 |
| 同一 token 不得跨书籍复用 | ❌ 唯一键只保证“一行” | **服务层** | 冲突后比对 `listing_id`，不同则拒绝（S3-B-2） |
| 禁止自购（R-04） | ❌ 跨表身份比较 | **应用/事务** | 读 `seller_id` 与 `buyer_id` 比对 |
| 只有买家本人能取消 | ❌ 行级权限 | **应用/事务** | `WHERE order_id=? AND buyer_id=?` |
| 旧 O1 请求不影响新 O2 | ❌ 需要状态判断 | **应用/事务** | 按 `order_id` 定位 + 状态校验 |
| 取消时间不早于下单时间 | ⚠️ 可写成 CHECK，但需 8.0.16+ | 数据库 + 应用 | `cancelled_at >= placed_at`（A-7） |
| 书籍状态与有效订单数一致 | ❌ 跨表等价关系 | **同一事务** | 提交前复核 `可售 ⇔ 0 条有效`、`已预留 ⇔ 1 条有效` |
| 不泄露他人订单 | ❌ | **查询条件与响应过滤** | 失败响应不含对方标识 |
| 价格两位小数（R-03） | ⚠️ `DECIMAL(10,2)` 可能隐式舍入 | **应用输入校验** | 写入前按字符串拒绝 12.345；受 `sql_mode` 影响 |

### 5.1 跨表状态说明（“已预留 ⇔ 恰一条有效订单”）

- 这个等价关系**只对事务提交后的稳定状态**成立；事务执行中间态、回滚后、以及两人并发写入时的瞬态都可能暂时不满足。断言 A-1/A-2 **不能**放在事务内部执行。
- `reservation_order.active_listing_id` 是**本行内部**的派生技术列（由本行 `order_status` 与 `listing_id` 算出），它只解决“同书有效订单 ≤ 1”这一**行间唯一性**问题，**不代表跨表状态**。
- 真正体现“书状态 ↔ 订单状态”跨表一致的是 `book_listing.availability_status`，它是**受控冗余**：不是从订单表算出来的，而是在下单/取消的**同一事务**里被显式更新。
- 三者分工是：`UNIQUE(active_listing_id)` 在订单表内兜底“同书至多一条有效订单”；`availability_status` 是**便于查询的受控冗余**，它本身**并不强制**“订单与书籍一致”——一致性靠下单/取消的**同一事务**写入维护、靠提交后的断言 A-1/A-2 检查；一个在订单表、一个在书籍表，不能互相替代。
- 若将来改为“读取时动态推导书籍状态”，可以取消这一冗余列（须同步改所有依赖它的查询与模型），但那属于设计变体，不是本版方案。
