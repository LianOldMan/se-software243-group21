## 3. 候选实体、标识与属性（概念层）

### 3.1 USER｜预置用户

| 概念属性 | 是否核心 | 意义与理由 |
|---|---|---|
| **user_id**（标识） | 必须 | 稳定区分不同用户，用于发布者、订单买家的身份关联；采用业务无关标识 |
| **account_code（预置账号标识）** | **必须、唯一**（实验二确定的存储选择） | 用于区分预置测试账号；不能为空、不得为空白串，同一账号标识不得重复。与逻辑设计 `user_account.account_code NOT NULL UNIQUE` 对齐；**不添加注册/密码功能**。 |

不要求分别创建 SELLER/BUYER 两个实体；用户名展示文字、密码或凭证策略不在实验一最终需求中确定，**不擅自新增存储密码要求**。

### 3.2 BOOK_LISTING｜书籍发布记录

| 概念属性 | 是否核心 | 意义与理由 |
|---|---|---|
| **book_id**（标识） | 必须 | 区分一本实物书的发布记录，供订单精确引用 |
| title | 必须 | 书名；R-01/FR-01，支持包含匹配 |
| author | 必须 | 作者；R-01/FR-03，支持筛选 |
| price | 必须 | 正数，最多两位小数；R-03 |
| condition | 必须 | 近全新／轻微使用痕迹／明显使用痕迹，固定三档 |
| description | 可选 | 卖家可填写的书籍说明 |
| status | 必须（业务可观察） | **可售**／**已预留**；与是否存在有效订单一致 |
| created_at | 必须 | 系统在成功发布时生成的时间，支持发布时间倒序 |

**卖家是谁**由 USER —发布→ BOOK_LISTING 联系表达；概念模型中不必额外把 `seller_id` 画成属性。逻辑转换成表时再由 B 以外键实现。

### 3.3 RESERVATION_ORDER｜预留订单

| 概念属性 | 是否核心 | 意义与理由 |
|---|---|---|
| **order_id**（标识） | 必须 | 每次成功预留的**唯一订单标识**；可区分旧 O1 和新 O2 |
| status | 必须 | **有效**／**已取消**；已取消仍保留记录，不物理删除 |
| **created_at（订单创建时间）** | **必须（实验二技术字段）** | 系统在下单成功生成，用于区分订单的时间顺序、历史检查与追溯；逻辑层对应 `reservation_order.placed_at NOT NULL DEFAULT CURRENT_TIMESTAMP(6)`。**属于建模新增的内部字段，不扩充实验一正式 FR**。 |
| **cancelled_at（取消时间）** | **条件必填**（数据库列允许 NULL） | 有效订单时必须为 `NULL`；取消成功后须记录取消时间，且保留原订单历史。逻辑层对应 `reservation_order.cancelled_at NULL`，与 `order_status` 的条件 `CHECK` 配合；这是实验二的审计/一致性辅助字段，不是实验一新增功能。 |

买家与关联书籍由两条联系表达。订单不能仅凭书籍 ID 定位取消，必须携带 **order_id**。

## 4. 三种联系及最小/最大基数

| 联系 | 从左到右解释 | 反方向解释 | 可选性 |
|---|---|---|---|
| USER —**发布**→ BOOK_LISTING | 每位用户可发布 **0..N** 条书籍记录 | 每条书籍记录有且仅有 **1** 位发布者 | 用户可以尚未发布；发布记录不能没有卖家 |
| USER —**预留**→ RESERVATION_ORDER | 每位用户可产生 **0..N** 条订单（包含历史已取消订单） | 每条订单有且仅有 **1** 位买家 | 用户可以没有订单；订单不能没有买家 |
| BOOK_LISTING —**对应订单**→ RESERVATION_ORDER | 一本书籍记录可有 **0..N** 条历史订单 | 每条订单有且仅有 **1** 条关联书籍记录 | 未被预留的书可无订单；订单不能没有书籍 |

**基数/可选性图例**：**父端 `1`**＝每条子记录必须且只能指向一个父记录（不能缺少发布者、订单买家或书）；**子端 `0..N`**＝一个父记录可暂时没有子记录，之后拥有任意多条记录（可选参与）。

**特别区分“0..N 历史订单”和“0..1 当前有效订单”**：前者是联系的历史基数，后者是**带状态条件的业务唯一性约束**，不改变“书籍—订单”的 1:0..N 联系。若把书籍—订单画成简单 1:1，取消后再次下单 O2 时会失去 O1 历史，违背 B-05/FR-07。

## 5. 必须保留的业务约束

| 约束编号 | 业务要求（给定—操作—预期的依据） | 实现责任提示（留待逻辑/物理设计） |
|---|---|---|
| C-01 | 发布者及订单买家必须引用现有预置用户；订单必须引用现有书籍记录 | 主外键可保障引用存在 |
| C-02 | 价格 > 0、至多两位小数；三档成色；必要字段不可为空 | 字段约束与校验；精度具体类型下一步决定 |
| C-03 | 同书**最多一个有效订单**；所有已取消旧订单仍保留 | 条件唯一性规则；可能需部分唯一索引、事务内串行化或等效应用逻辑；**普通外键不能保证** |
| C-04 | 用户不得预留自己发布的书 | 必须比较订单买家与书籍发布者，普通外键本身不能独立保证 |
| C-05 | 下单创建有效订单与书籍变已预留、取消订单与恢复可售必须一致；**在每次已提交的稳定数据库状态，对任一本书断言：书籍状态＝“已预留” ⇔ 恰有一笔该书状态＝“有效”的订单** | 应在同一事务下锁定与更新，避免部分提交和竞争覆盖；外键仅保证关联存在。走查中核验“书已预留但无有效订单”和“有有效订单而书可售”两类异常均为 **0 条**（此为预期断言，未实测）。 |
| C-06 | 只有当前有效订单的**买家本人**可以取消；旧 O1 请求不得取消 O2 或释放其书籍 | 根据 `order_id` 定位，核验归属与状态，再按事务条件更新 |
| C-07 | 默认检索按发布时间倒序；当前状态可观察，书名/作者可包含搜索 | 由 BOOK_LISTING 字段与查询实现；无需新增“搜索条件”实体 |

本阶段只**识别约束**，不是已经通过程序验证。指导书提醒的“外键仅保证引用存在，身份与跨表更新需应用/事务负责”已明确纳入。

## 8. 概念属性与逻辑表的明确命名映射（回应 B/C 的 C-04）

**概念设计以业务意义为主，数据库设计以物理字段名称为准；下面均表示同一数据含义，不是增加新实体。**

| 概念实体／属性（本稿） | 逻辑表／字段（第二步草案） | 一致性说明 |
|---|---|---|
| USER | `user_account` | 单一预置账号实体，承担发布者和买家双重角色 |
| USER.`user_id` | `user_account.user_id` | 非业务主键 |
| USER.`account_code` | `user_account.account_code` | 必填、唯一，禁止仅空格 |
| BOOK_LISTING | `book_listing` | 一本实物书对应一条发布记录 |
| BOOK_LISTING.`book_id` | `book_listing.listing_id` | 发布记录唯一标识，改名但不改变含义 |
| BOOK_LISTING.`title`, `author`, `price` | `book_listing.title`, `author`, `price` | 必填书名／作者／价格 |
| BOOK_LISTING.`condition` | **`book_listing.condition_grade`** | 统一采用现有 SQL/数据字典字段名；**不采用 condition_level**，避免双重命名 |
| BOOK_LISTING.`description` | `book_listing.description` | 选填说明 |
| BOOK_LISTING.`status` | `book_listing.availability_status` | “可售／已预留”，与订单状态区分 |
| BOOK_LISTING.`created_at` | `book_listing.published_at` | 系统生成的**发布记录创建时间**，不是图书出版日期 |
| RESERVATION_ORDER | `reservation_order` | 预留订单与取消历史 |
| RESERVATION_ORDER.`order_id` | `reservation_order.order_id` | 同一订单唯一标识 |
| RESERVATION_ORDER.`status` | `reservation_order.order_status` | 有效／已取消 |
| RESERVATION_ORDER.`created_at` | `reservation_order.placed_at` | 下单时间必填、系统生成 |
| RESERVATION_ORDER.`cancelled_at` | `reservation_order.cancelled_at` | 有效时 NULL、取消后有值 |

**时间先后与取消安全的边界**：时间字段用于查询和审计，不作为取消对象的唯一依据。取消必须始终根据**具体 order_id + buyer_id + 当前有效状态**定位和校验；即使因相同时钟精度导致订单时间相同，也不能让旧 O1 请求修改新 O2。
