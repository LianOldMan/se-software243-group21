## 1. 由概念实体转为三张关系表

| 中文实体 | 建议物理表名 | 主键 | 主要外键 | 功能与需求来源 |
|---|---|---|---|---|
| 用户（预置账号） | `user_account` | `user_id` | 无 | B-02/03：同一用户可发布书，也可作为买家下单；不拆买家表、卖家表 |
| 书籍发布记录 | `book_listing` | `listing_id` | `seller_id → user_account.user_id` | FR-01～04：每条记录代表一本实物书；记录发布者、描述、状态与发布时间 |
| 预留订单 | `reservation_order` | `order_id` | `buyer_id → user_account.user_id`；`listing_id → book_listing.listing_id` | FR-05～08：一次预留一条订单，取消后保留历史；同书同时至多一条有效订单 |

**联系与可选性**：用户 1 ↔ 书籍 0..N（每本书必须有一个卖家）；用户 1 ↔ 订单 0..N（每张订单必须有一个买家）；书籍 1 ↔ **历史**订单 0..N（每张订单必须关联一本书）。三个非空外键承接概念 ER 的三条联系。**不可将“历史订单多条”误写成“同时有效订单可多条”**。

## 2. 数据字典：`user_account`（预置账号）

| 字段 | 中文含义 | 类型与长度（MySQL） | 可空 | 默认值 | 键 / 限制 | 理由 |
|---|---|---|---|---|---|---|
| `user_id` | 用户编号 | `BIGINT UNSIGNED` | 否 | 自增 | **PK** | 账户身份稳定；不以可变用户名作下游 FK |
| `account_code` | 预置账号标识 | `VARCHAR(64)` | 否 | 无 | **UNIQUE**；去除首尾空格后非空 | 区分预设用户，既可作发布者又可作买家 |

**边界**：不新建注册、找回密码、真实支付或专属卖家角色。账号总数（C-Q-12）和登录验证方案尚未决定，因此本表**没有擅自加入密码、手机号、实名、权限等级**。同一用户可同时出现在 `seller_id` 和别的书的 `buyer_id` 中。

## 3. 数据字典：`book_listing`（书籍发布记录）

| 字段 | 中文含义 | 类型与长度（MySQL） | 可空 | 默认值 | 键 / 限制 | 理由 |
|---|---|---|---|---|---|---|
| `listing_id` | 发布记录编号 | `BIGINT UNSIGNED` | 否 | 自增 | **PK** | 一条记录对应一本实物书；书名不唯一 |
| `seller_id` | 发布者用户编号 | `BIGINT UNSIGNED` | 否 | 无 | **FK → user_account.user_id**；删除受限 | 每条记录必须且仅有一个发布者 |
| `title` | 书名 | `VARCHAR(120)` | 否 | 无 | 非空白（应用检查） | R-01 必填，FR-03 书名包含匹配 |
| `author` | 作者 | `VARCHAR(100)` | 否 | 无 | 非空白（应用检查） | R-01 必填，FR-03 作者筛选 |
| `price` | 价格 | `DECIMAL(10,2)` | 否 | 无 | `CHECK(price > 0)` | 精确保存金额，避免浮点误差 |
| `condition_grade` | 成色 | `VARCHAR(16)` | 否 | 无 | **CHECK**：近全新／轻微使用痕迹／明显使用痕迹 | Q-05 固定三档 |
| `description` | 选填说明 | `VARCHAR(500)` | **是** | `NULL` | 无 | R-01 可选；不强迫填写 |
| `availability_status` | 当前可售状态 | `VARCHAR(12)` | 否 | **可售** | **CHECK**：可售／已预留 | FR-04～08 列表/详情与预留状态 |
| `published_at` | 发布时间 | `DATETIME(6)` | 否 | 系统 `CURRENT_TIMESTAMP(6)` | **不可让卖家自填/修改**；排序索引 | v0.5.6 定义“成功创建发布记录的时间”，不是图书出版时间 |

**设计决定 L-01：状态暂采用持久化字段。** 该方案让书籍列表、详情读取直接得到状态，配合 `reservation_order` 有效订单数量作为一致性校验；它是**可维护的受控冗余**，不是“两个状态可以各自随意更新”。下单/取消必须**同一事务**更新订单与书籍状态，并在提交前核对 `可售 ⇔ 没有有效订单`、`已预留 ⇔ 恰有一条有效订单`。也可在后续由全组评审后改成动态推导状态，但必须同步修改数据字典与表间关系图。

**设计决定 L-02：价格录入精度由应用先验证。** `DECIMAL(10,2)` 与 `CHECK(price > 0)` 能限制存储范围及正数，但某些数据库转换可能**自动舍入**例如 12.345；必须在写入前按输入字符串拒绝超过两位小数，不能只靠 DECIMAL 宣称已满足 R-03。

## 4. 数据字典：`reservation_order`（预留订单）

| 字段 | 中文含义 | 类型与长度（MySQL） | 可空 | 默认值 | 键 / 限制 | 理由 |
|---|---|---|---|---|---|---|
| `order_id` | 订单编号 | `BIGINT UNSIGNED` | 否 | 自增 | **PK** | 旧订单 O1 与新订单 O2 不混淆 |
| `listing_id` | 被预留的书籍发布编号 | `BIGINT UNSIGNED` | 否 | 无 | **FK → book_listing.listing_id** | 每条订单必须对应一本书 |
| `buyer_id` | 买家编号 | `BIGINT UNSIGNED` | 否 | 无 | **FK → user_account.user_id** | 归属校验、禁止越权取消 |
| `order_status` | 订单状态 | `VARCHAR(12)` | 否 | **有效** | **CHECK**：有效／已取消 | 历史订单保留，当前订单有效与否可查 |
| `placed_at` | 下单时间（设计增加） | `DATETIME(6)` | 否 | `CURRENT_TIMESTAMP(6)` | 系统生成 | 用于追溯请求先后；**实验一未将此列为强制功能** |
| `cancelled_at` | 取消时间（设计增加） | `DATETIME(6)` | **是** | `NULL` | 有效订单必须为空、取消时写入 | 可核对历史；**是建议附加字段** |
| `request_token` | 同一逻辑下单请求的幂等标识（设计增加） | `CHAR(36)` | 否 | 无 | **UNIQUE(buyer_id, request_token)** | 首次下单成功却丢失回包时，同一买家以同一 token 重试不新建订单 |
| `active_listing_id` | 当前有效订单的书籍编号（技术派生） | `BIGINT UNSIGNED` **生成列** | **是**（取消订单派生 NULL） | 表达式生成 | **UNIQUE**，派生 `CASE WHEN order_status='有效' THEN listing_id ELSE NULL END` | 精确限制同书**至多一个有效订单**，允许任意多条已取消历史订单 |

**设计决定 L-03：有效订单的唯一性。** 示例以 MySQL 生成列 `active_listing_id` 加唯一索引保证：有效订单填书籍编号；取消历史派生为 `NULL`。MySQL 唯一索引允许多行 NULL，因此同书历史取消记录可有多条，而有效订单同书最多一条。不能用 `UNIQUE(listing_id, order_status)`，否则同一本书会被错误地限制为最多**一条已取消历史订单**。这种“按状态唯一”的**实现技术是本阶段提议**，不是教师或实验一规定必须使用的语法。

**设计决定 L-04：请求重放。** `request_token` 由界面/服务为**一次用户下单动作**生成；同一次网络重试必须复用原 token，新下单动作须使用新 token。数据库唯一键防止相同买家相同 token 形成两条订单；发生唯一冲突时，服务应查询并返回**原订单结果**，不能直接当作全新的失败；仍须配合书籍行锁/事务以及业务身份核验。这是为 UC-04 A5、AC-04-5 提供的**技术候选**，需要 B/C 复核。

**设计决定 L-05：取消状态**：合法取消将 `order_status` 置“已取消”并填写 `cancelled_at`，不删除订单；取消已取消的 O1 不会触及后来新建的 O2。数据库本身不能根据一条 FK 限制“买家不能是书的卖家”，由订单事务读取 `seller_id` 并做 R-04 校验。

## 5. 建议的主键、外键、索引和事务责任

| 类别 | 名称 / 位置 | 作用 |
|---|---|---|
| PK | `user_account.user_id`、`book_listing.listing_id`、`reservation_order.order_id` | 稳定、单列实体唯一标识 |
| FK | `book_listing.seller_id` → `user_account.user_id` | 不能发布到不存在的用户 |
| FK | `reservation_order.buyer_id` → `user_account.user_id` | 订单必须属于合法预置账号 |
| FK | `reservation_order.listing_id` → `book_listing.listing_id` | 订单必须指向存在的书籍记录 |
| UNIQUE | `user_account.account_code` | 预置账号不重复 |
| UNIQUE | `reservation_order.active_listing_id`（生成列） | 同书最多一条有效订单，取消历史不限次数 |
| UNIQUE | `reservation_order(buyer_id, request_token)` | 同一逻辑下单请求幂等 |
| INDEX | `book_listing(published_at DESC, listing_id DESC)` | 默认从新到旧的稳定排序，发布时间相同用 ID 决胜 |
| INDEX | `book_listing(availability_status, published_at DESC)` | “仅看可售”及排序的候选优化 |
| INDEX | `reservation_order(listing_id, order_status)` | 通过书籍找有效/历史订单；辅助一致性核对 |
| INDEX | `reservation_order(buyer_id, order_status)` | 买家查自己的有效订单及取消入口 |

**查询提醒**：FR-03 使用 `LIKE '%关键词%'` 包含匹配；普通 B-Tree 对前置通配符通常不能有效定位范围，**不宣称上述索引已经满足 NFR-01 的 95% ≤ 2s**。这一指标须在 1000 条书、10 并发、每类不少于 100 请求的真实环境中验证；本阶段无 SQL 实测。

**必须由应用/事务负责的事**：
1. **禁止自购**：锁定书籍并读取发布者，校验 `buyer_id != seller_id`（R-04）。普通 FK/CHECK 无法跨表验证两者身份。
2. **原子下单**：在同一事务内检查书籍仍可售、确保无另一有效订单、创建订单并将书籍改为“已预留”；并发由行锁加生成列唯一索引兜底。成功或回滚必须完整发生。
3. **原子取消**：按**具体 `order_id`** 定位、验证 `buyer_id` 与有效状态，更新该订单为已取消，且仅在没有其他有效订单时恢复书籍“可售”；提交前再次确认，不能按书号取消其他买家的新单。
4. **统一锁顺序**：两个状态变更流程都先锁相关 `book_listing` 行，再检查/锁定对应订单行，降低死锁与旧请求覆盖新预留的风险；服务在唯一键冲突/死锁时给出正确提示或安全重试。
5. **状态校验与异常检测**：表上 FK、CHECK、UNIQUE 不足以单独保证“书籍状态”和有效订单数跨表一致；异常发现和人工/服务修复政策属 **B-Q-11 待确认**，本阶段不擅自采纳自动自愈。

## 6. 关键函数依赖与规范化（初步检查）

| 表 | 主要函数依赖 | 规范化说明 |
|---|---|---|
| `user_account` | `user_id → account_code`；`account_code → user_id` | 非键属性依赖单列主键，无混合买家/卖家两套重复账户 |
| `book_listing` | `listing_id → seller_id,title,author,price,condition_grade,description,availability_status,published_at` | 所有普通字段依赖唯一发布记录；书名/作者非唯一；不用标题决定作者/卖家 |
| `reservation_order` | `order_id → listing_id,buyer_id,order_status,placed_at,cancelled_at,request_token`；`(buyer_id,request_token) → order_id` | 订单不复制书名、书价、卖家账号；这些按 FK 查询，避免传递依赖；生成列 `active_listing_id` 是唯一性技术字段，逻辑上由 `listing_id,order_status` 推得 |

三张表主键都只有一个字段，因此不存在**复合主键的一部分**决定非键属性的部分依赖；在上述字段及语义下达到 **3NF 的基础目标**。需要特别说明：`book_listing.availability_status` 是为了界面查询而保留的**受控冗余状态**，虽不直接违反“单表非键属性依赖键”的 3NF 判定，却增加了**跨表同步的更新异常风险**；必须有事务一致性保障，不能简单称“满足 3NF 就不会有任何异常”。

## 7. 对应三个场景的字段变化预演（尚未执行 SQL）

| 场景 | 给定数据 | 操作 | 预期变化与数据库约束依据 |
|---|---|---|---|
| **S1 正常下单** | U1 发布 L1（可售）；U2 ≠ U1 | U2 首次申请预留 L1 | `reservation_order` 新增 O1：`buyer_id=U2`、`listing_id=L1`、`order_status=有效`、`active_listing_id=L1`；L1 状态改为“已预留”；三 FK/唯一生成列与事务共同保证 |
| **S2 取消后再下单** | O1 属于 U2、状态有效；L1 已预留；U3 ≠ U1 | U2 取消 O1，之后 U3 预留产生 O2，旧 O1 取消请求重发 | O1 变“已取消”且保留，`cancelled_at` 填时间、派生有效编号 NULL；L1 先可售后已预留；O2 有效；旧 O1 重放不修改 O2；依赖订单主键、买家校验、事务与唯一约束 |
| **S3 同书竞争/重试** | U2、U3 都不是卖家；L1 可售 | 几乎同时预留；U2 成功但回包丢失重试 | **至多**一笔有效订单；失败方不获得对方身份信息，L1 最终一致“已预留”；U2 使用相同 token 重试返回原单，绝不生成第二个有效订单；唯一生成列 + 请求 token + 事务保护 |

这些是**设计推演**，不是实际 SQL 成功截图或性能测试结果；下一阶段 C 主责需将其整理为指导书明确要求的正式“给定数据—操作—预期变化—约束依据”走查与独立表间关系图。
