## 一、业务边界与需要长期保存的数据

按实验一的 **B-01～B-06、FR-01～08、R-01～05、Q-01～08**：

1. **发布**：卖家通过预置账号发布一本实物书，必填书名、作者、价格、成色，可填写说明；发布成功由系统产生唯一发布记录与发布时间，状态初始“可售”。价格大于0、至多两位小数，成色限定三档。输入错误只反馈、不保存无效新记录。（FR-01/02、R-01/03、Q-05）
2. **检索和查看**：按书名、作者包含匹配及 AND 组合，列表展示价格、成色、当前状态，默认按系统生成的发布时间倒序排序。无需保存“临时检索关键词”为独立实体。（FR-03/04、R-02/05、Q-01～03）
3. **预留下单**：订单必须对应一个**买家账号**和一条**书籍发布记录**；成功产生唯一订单标识，订单状态“有效”，书籍状态“已预留”。同书同一时刻最多一个有效订单；不能预留自己发布的书；重复或竞争预留不产生第二条有效订单。（FR-05/06、R-04）
4. **取消**：仅订单买家本人可以取消指定的有效订单，状态设为“已取消”，历史保留；没有其他新有效订单时，书籍恢复“可售”；已取消旧订单不能影响后来有效的新订单。（FR-07/08、AC-05-1～7、NFR-02）
5. **范围外**：注册/找回密码、真实支付/退款、物流、交易完成、评价、推荐、卖家下架、管理员后台等均不建独立实体。预置账号**数量与分配未定**，不能臆造具体人数。（B-02/06、§1.2、C-Q-12）

## 二、概念实体与属性（尚不约定 SQL 类型）

| 实体（英文名） | 唯一标识 | 本阶段必须表达的属性及意义 | 设计建议但非既定要求 | 来源 |
|---|---|---|---|---|
| 用户 **User** | `user_id`：唯一标识预置账号 | 实际业务角色由关系表达，同一用户可既是发布者也能作为买家 | `login_name`：便于标记/选择预置账号；是否需要其他认证资料留到逻辑设计；不直接建立互斥 Buyer/Seller 表 | B-02/03、UC-01/04/05 |
| 书籍发布记录 **BookListing** | `listing_id`：唯一定位一条发布记录（=一本实物书） | `title` 书名、`author` 作者、`price` 价格、`condition` 成色、`description` 可选说明、`listing_status` 可售/已预留、`created_at` 系统生成发布时间；**发布者由 User—BookListing 的联系表达** | 具体数据库价格类型、长度、字符集、状态冗余维护方式由逻辑设计决定 | FR-01～04、R-01/03/05、Q-01/03/05 |
| 预留订单 **ReservationOrder** | `order_id`：每笔预留的唯一标识，取消必须定向到它 | `order_status` 有效/已取消；**买家与书籍分别由概念联系表达**；取消后仍保留整笔历史订单 | `created_at` 建议记录下单时间、`canceled_at` 建议记录取消时间（仅取消后有值），**这两者不是实验一强制的展示字段** | FR-05～08、B-04/05、AC-04/05 |

> 概念 ER 图只表达实体及业务联系；逻辑设计阶段才把“发布者、买家、所订书籍”的联系转换为外键字段。**不要因为本图没有 `seller_id` / `buyer_id` / `listing_id` 外键列，就误判缺少关联**。

## 三、联系、基数与可选性（图上须体现）

| 关系 | 端点及基数 | 参与可选性 | 业务解释 |
|---|---|---|---|
| **发布**：User — BookListing | 一个 User → **0..N** 条 BookListing；每条 BookListing → **恰好 1** 个 User | 用户可以尚未发布书；每条书籍记录必须存在发布者 | 一个账号可兼任卖家和买家，但某次发布的卖家唯一 |
| **下单预留**：User — ReservationOrder | 一个 User → **0..N** 条 ReservationOrder；每笔 ReservationOrder → **恰好 1** 个 User | 用户可以没有订单；每笔订单必须有买家 | 买家应从预置账号集合中确定；不允许买家与所订书籍的发布者为同一用户 |
| **关联历史订单**：BookListing — ReservationOrder | 一本 BookListing → **0..N** 条 ReservationOrder；每笔 ReservationOrder → **恰好 1** 条 BookListing | 一本书可以从未被预留；订单不能不关联书籍 | “0..N”表示**跨时间保留多笔已取消/历史订单**，不是同时允许 N 笔有效订单 |

**额外业务约束，不等于联系基数**：对每条书籍，`count(相关订单 where status='有效') ≤ 1`；存在唯一有效订单时书籍应标“已预留”，否则“可售”。这是跨实体/跨状态的业务不变量，不能只依赖 ER 图基数或外键直接保证。后续设计要明确事务/条件更新/唯一性策略，且旧 O1 的重复取消不得影响新 O2。

## 四、核心数据来源与需求追踪

| 数据与联系 | 支持的 FR/UC | 需要检查的事实 |
|---|---|---|
| User 与发布关系；BookListing 书名/作者/价格/成色/说明 | FR-01/02，UC-01 | 必填与正数价格、三档成色、一个发布对应一本实物书、失败不创建 |
| BookListing 的状态与系统发布时间 | FR-03/04，UC-02/03 | 结果默认倒序、列表状态筛选、详情字段与原记录一致 |
| User 与订单的买家关系；订单与书籍的联系；order_id | FR-05/06，UC-04 | 身份、禁止自购、一次预留一条有效订单、失败不改原订单 |
| order_status 与书籍当前状态，历史订单保留 | FR-07/08，UC-05 | 指定取消、越权/重复拒绝、并发与旧订单保护 |
| 记录规模与并发场景 | NFR-01/02/03 | 属于**未来拟定的检查条件**，尚无性能/可靠性/易用性实测结果 |

## 五、不能在本步擅自确定的设计细节

- **B-Q-04**：未登录匿名检索/查看的许可范围没有组内最终决定；概念 ER 不因此新增访客账户表。
- **B-Q-11**：书籍显示可售却存在有效订单的历史异常数据如何修复，尚待决定；设计层先明确**拒绝不一致的写入**和不变量，不编造自动修复程序。
- **B-Q-12**：同一卖家重复发布同一本实物书的判重标准尚未决定；**不能把书名 + 作者设成唯一键**（不同实物书完全可能同名同作者）。
- **C-Q-12**：预置账号的数量、角色分配待定；不新增“卖家/买家互斥角色”限制。
- **技术方案待下一步**：主外键、字段类型/长度、书籍状态是否冗余存储、有效订单唯一性如何在并发下保证、事务与故障恢复，均在表结构及数据字典阶段提出方案并核对；不要宣称已通过 SQL 验证。
