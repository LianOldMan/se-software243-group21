## 1. 设计范围、重要前提和核心场景

围绕 **UC-04 下单预留、UC-05 取消订单**，适度引用 UC-01 发布与 UC-02/03 检索查看。系统预置账号、一条发布记录代表一本实物书；同一用户可作买家和卖家但不能预留自己发布的书。下单**仅代表预留，无支付**；不增加注册、物流、退款、订单完成、评价等需求。需求范围仍为 **8 FR、5 UC、3 NFR**，四项待确认问题 B-Q-04/B-Q-11/B-Q-12/C-Q-12 暂不升级为规则。

数据库设计参照 `user_account`、`book_listing`、`reservation_order` 三张表（设计层、未部署），具体逻辑约束：单书可有多条取消历史但**同时至多一条有效订单**；`availability_status` 为受控冗余，**下单/取消必须同一事务维护**；订单取消须按原 `order_id` 和当前买家身份判断，旧订单不得误释放后来的新预留。

以下类、对象及方法名称为**软件设计抽象，不是现有 Java 程序源码或 API**。

## 2. 类与数据库之间的映射（A 类图的共同输入）

| 类（建议统一英文） | UML 职责 | 关键属性（命名尽量对应字典） | 操作（名称固定供 B/C 使用） |
|---|---|---|---|
| `UserAccount` | 预置账号身份的实体类 | `userId: Long`、`accountCode: String` | 本次无独立业务变更操作 |
| `BookListing` | 一本实物书的发布记录和可售状态 | `listingId: Long`、`sellerId: Long`、`title: String`、`author: String`、`price: Decimal`、`conditionGrade: String`、`description: String?`、`availabilityStatus: ListingStatus`、`publishedAt: DateTime` | `isAvailable(): Boolean`、`markReserved(): void`、`markAvailable(): void` |
| `ReservationOrder` | 预留订单实体、状态及取消历史 | `orderId: Long`、`listingId: Long`、`buyerId: Long`、`orderStatus: OrderStatus`、`placedAt: DateTime`、`cancelledAt: DateTime?`、`requestToken: UUIDString`、`/activeListingId: Long?`（派生、只读） | `isActive(): Boolean`、`markCancelled(dbNow: DateTime): void` |
| `ReservationController` | 接收下单与取消请求、映射返回信息（边界类） | 无独立业务持久字段 | `issueRequestToken(buyerId: Long): UUIDString`（下单前准备步骤）、`reserveBook(buyerId: Long, listingId: Long, requestToken: UUIDString): ReservationResult`、`cancelReservation(buyerId: Long, orderId: Long): CancelResult` |
| `ReservationService` | 编排校验、锁、幂等、事务与跨表状态变更（控制类） | 依赖三个 Repository | `issueRequestToken(buyerId: Long): UUIDString`（服务端预先签发）、`placeReservation(buyerId: Long, listingId: Long, requestToken: UUIDString): ReservationResult`、`cancelReservation(buyerId: Long, orderId: Long): CancelResult` |
| `UserAccountRepository` | 读取并验证预置账号 | 无（持久化端口） | `findById(userId: Long): UserAccount?` |
| `BookListingRepository` | 读取和锁定书籍发布记录、更新状态 | 无（持久化端口） | `lockById(listingId: Long): BookListing?`、`updateAvailability(listingId: Long, state: ListingStatus): void` |
| `ReservationOrderRepository` | 订单增查、锁定与条件取消 | 无（持久化端口） | `findByBuyerAndToken(buyerId: Long, token: String): ReservationOrder?`、`findById(orderId: Long): ReservationOrder?`、`lockById(orderId: Long): ReservationOrder?`、`insert(order: ReservationOrder): ReservationOrder`、`cancelIfActive(orderId: Long, buyerId: Long, dbNow: DateTime): Int`、`countActiveByListing(listingId: Long): Int` |

**图示约定**：

- `UserAccount 1 → 0..N BookListing`（发布者关联）；`UserAccount 1 → 0..N ReservationOrder`（买家关联）；`BookListing 1 → 0..N ReservationOrder`（历史订单关联）。订单强制指向单一用户及书籍；不要把历史订单误画成 1:1。
- `ReservationController → ReservationService` 为调用依赖；`ReservationService → 各 Repository` 为依赖；实体之间可表达关联但不扩充数据库表。**同一个 UserAccount 可承担两个角色**。
- `activeListingId` 是订单的**派生技术属性**，不是新增实体、不是外键、不对外提供任意修改操作；持久化层的条件唯一性由生成列+UNIQUE 保障（参照 MySQL 设计假设）。
- `ListingStatus = {可售, 已预留}`；`OrderStatus = {有效, 已取消}`。不要擅自画“已付款/已完成/已发货”等状态。
- `Transaction/UnitOfWork` 可以作为服务内事务边界注释或 `«in transaction»` 框，不要求另外增加实际持久化实体或业务类。

## 3. 关键方法输入、输出与失败契约（五图共同依据）

| 操作 | 输入 | 正常输出 / 数据变化 | 异常与保证 |
|---|---|---|---|
| `ReservationController/Service.issueRequestToken` | `buyerId` | 服务在首次下单动作**发出前**签发 36 位规范 UUID 并交客户端持有；新动作新 token，同动作网络重试复用 | 账号不可用则拒绝签发；这属于本实验二已选的技术契约，不新增独立业务用例或支付等功能 |
| `ReservationService.placeReservation` | `buyerId, listingId, requestToken` | `ReservationResult{orderId, listingId, status='有效', replayed=false}`；一笔有效订单创建且书籍变“已预留”，同事务提交 | 无效账号、书不存在/不可售、自购、重复 token 跨书冲突、并发冲突或系统故障；失败不产生半完成数据 |
| 同 token 幂等重试（同方法） | 与首次逻辑动作**相同买家、相同 listing、相同 token** | 返回与原 `orderId` 对应的**当前订单状态**，`replayed=true`；已取消旧单也不得重建订单 | token 相同而 `listingId` 不同，拒绝 `TOKEN_TARGET_MISMATCH`；不能把 A 书的订单当作 B 书成功 |
| `ReservationService.cancelReservation` | `buyerId, orderId` | `CancelResult{orderId, status='已取消'}`；对应订单保留，`cancelledAt` 为 DB `NOW(6)`，同事务将无有效订单的书恢复可售 | 非订单买家、旧单/重复取消、订单不存在、数据库失败；旧请求**不能释放新订单**，失败不改变状态 |
| `BookListing.isAvailable` | 无（当前实体） | 当前状态是否“可售” | 不保证没有跨表异常，事务内仍须查有效订单/唯一约束 |
| `ReservationOrder.markCancelled` | `dbNow` | 将本对象状态置“已取消”、填取消时间；**持久化条件更新**仍由 Repository/事务执行 | 已取消不得重复转换，`dbNow<placedAt` 不合法 |

**建议的结果/错误枚举**：`RESERVED`、`EXISTING_RESULT`、`CANCELLED`；`INVALID_USER`、`LISTING_NOT_FOUND`、`ALREADY_RESERVED`、`SELF_RESERVATION`、`TOKEN_TARGET_MISMATCH`、`ORDER_NOT_FOUND`、`FORBIDDEN_CANCEL`、`ORDER_NOT_ACTIVE`、`CONCURRENT_CONFLICT`、`SYSTEM_FAILURE`。这是软件设计的状态表达，不增加订单数据库状态值。

## 4. 顺序图/协作图统一对象与编号（B 先按此画 v0.1）

选取**“买家预留一本可售书籍 UC-04，含已预留/重复请求备选分支”**作为同一场景，顺序图与协作图使用同一组对象：

`buyer:Actor` → `ui:ReservationController` → `svc:ReservationService`，并由 `svc` 调用 `users:UserAccountRepository`、`books:BookListingRepository`、`orders:ReservationOrderRepository`。

**建议稳定的消息编号**（两个 UML 图之间一致，复杂条件/事务可加 `alt/opt` 或编号后缀，B 可在审查时提出等价调整）：

| 编号 | 发送方 → 接收方 | 统一方法/消息（示意参数） | 说明 |
|---|---|---|---|
| 1 | buyer → ui | `reserveBook(buyerId,listingId,requestToken)` | 接收请求；**此前已通过 `issueRequestToken` 预签发 token，不在本图中重复画准备环节** |
| 1.1 | ui → svc | `placeReservation(buyerId,listingId,requestToken)` | 业务入口 |
| 1.1.1 | svc → users | `findById(buyerId)` | 账号校验；UUID 格式在 svc 校验 |
| 1.1.2 | svc → orders | `findByBuyerAndToken(buyerId,requestToken)` | **先查幂等命中**；同 token/同书返回旧状态，跨书拒绝 |
| 1.1.3 | svc → books | `lockById(listingId)` | **新动作**进入同一事务、锁书籍、检查状态、自购 |
| 1.1.4 | svc → orders | `findByBuyerAndToken(buyerId,requestToken)` | 获锁后再次检查 token，避免竞争中的重复新单 |
| 1.1.5 | svc → orders | `countActiveByListing(listingId)` | 核对无已有有效单（索引也做最终兜底） |
| 1.1.6 | svc → orders | `insert(order)` | 新增有效订单，DB 条件 UNIQUE 保障同书≤1有效 |
| 1.1.7 | svc → books | `updateAvailability(listingId,已预留)` | 同事务更新，提交成功方可返回 |
| 1.2 | svc → ui | `ReservationResult / Error` | 含 `orderId/status/replayed` 或拒绝码 |
| 2 | ui → buyer | 显示预留结果 | 前端反馈，非新增服务方法 |

**事务说明**：在 `1.1.3` 前开启服务事务，`1.1.7` 后提交；任一失败事务回滚。正式图必须标出至少一个 `alt` 异常分支，如已预留、卖家自购、token 跨书复用；如果使用不同参数/方法，**必须先在本约定和类图/双图同步修订**。`commit/rollback` 可画事务注释，不作为 Entity 的持久化业务方法。

## 5. 状态图与活动图选型（C 先按此画 v0.1）

**状态图对象：`ReservationOrder`。** 初始节点（尚无订单记录）经成功创建 → `有效`；`有效` 经 `cancelReservation [buyerId==order.buyerId && status==有效]` → `已取消`（执行 DB `NOW(6)`、更新对应书籍状态）。`已取消` 为保留历史的**业务终态**，不能跳回有效；再次预留只能创建**新 orderId** 的订单。失败分支不得创建新的数据库订单状态；自购、竞争、重复请求等是服务拒绝/重放行为，不是新增 OrderStatus 值。

**活动图核心：UC-04 下单预留。** 有起始与结束；输入账号/书籍/token → 验证账号和 UUID → 幂等命中？ → 相同 listing 返回已有结果、不同 listing 拒绝 → 事务锁定书籍 → 检查书籍/卖家身份/可售/无有效单 → 生成有效订单并更新状态 → 提交/反馈；异常路径回滚并输出明确原因。可按参与者 / Controller / Service / Repository 设置泳道，**至少画出正常出口和两条异常出口**，所有活动方法与本约定一致。

## 6. 六个统一走查场景（必须覆盖 3 正常 + 3 异常/边界）

| 编号 | 类型 | 给定条件与操作 | 预期及核对的模型 |
|---|---|---|---|
| SD-N1 | 正常 | 买家 U2 对 U1 发布的可售 L1 发起首次预留 | 新建 O1 有效、L1 已预留；类操作/顺序图/状态图/活动图均能解释 |
| SD-N2 | 正常 | O1 的买家 U2 正常取消自己的有效订单 | O1 已取消并保留历史、取消时间来自 DB、L1 恢复可售；状态图/类方法一致 |
| SD-N3 | 正常 | U2 取消 O1 后，U3 使用新 token 预留 L1 | 新建 O2 有效、旧 O1 仍取消、L1 已预留；不可复活旧 O1 |
| SD-E1 | 异常 | U2 重复提交**同一** token 与 L1；首笔已经创建但响应丢失 | 返回原 `orderId` 当前状态，不产生第二笔；同 token 跨书使用则拒绝 |
| SD-E2 | 异常 | U2 对 O1 再次取消，且之后 O2 已有效 | 拒绝重复取消且 O2/L1 不变；订单主键和状态守卫必须正确 |
| SD-E3 | 异常 | U3 尝试取消 U2 的有效订单 O1 | 越权拒绝，O1/L1 保持不变 |
| SD-E4（加分候选） | 边界 | 两名买家争抢 L1，或卖家试图预留自己的 L1 | 同书至多一笔有效，卖家自购拒绝；设计推演，非实际并发实测 |

走查记录格式固定：**初始条件 → 调用及关键消息 → 预计对象状态/数据变化 → 对应需求与图 → 发现与修改**。三人共同走过六个场景，不仅由 C 独立完成。
