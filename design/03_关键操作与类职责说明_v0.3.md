## 1. 设计范围与类的分层

本实验选择 **UC-04 下单预留＋UC-05 取消订单** 作为统一业务。保持预置账号、一条发布记录对应一本实物书、无支付。实验一仍为 8 FR／5 UC／3 NFR。**新绘的服务/仓储类是分析设计层对象，不是新数据库表或已经存在的源码。**

| 分层／类型 | 类 | 职责 | 与数据库/需求关系 |
|---|---|---|---|
| 实体 `«entity»` | `UserAccount` | 表示预置账号；同一账号可充当卖家和买家 | `user_account`；`userId` 为 PK；不加入注册和密码逻辑 |
| 实体 `«entity»` | `BookListing` | 表示一本实物书的发布记录，判断可售并更改受控状态 | `book_listing`；`sellerId` FK；FR-01～04 及下单/取消观察状态 |
| 实体 `«entity»` | `ReservationOrder` | 保存一次预留的买家、书籍、状态及取消历史 | `reservation_order`；`buyerId/listingId` FK；FR-05～08 |
| 边界 `«boundary»` | `ReservationController` | 接收请求、把结果转换为可理解的成功/拒绝信息；不直接写表 | UC-04／UC-05 输入、输出 |
| 控制 `«control»` | `ReservationService` | 负责用户与 UUID 校验、幂等、统一锁顺序、原子事务和错误分类 | 两表状态一致性、禁止自购、历史订单安全 |
| 持久化端口 `«repository»` | `UserAccountRepository` | 按用户 ID 查询预置账号 | `user_account` |
| 持久化端口 `«repository»` | `BookListingRepository` | 按书籍 ID 查询、锁行及持久化可售状态 | `book_listing` |
| 持久化端口 `«repository»` | `ReservationOrderRepository` | 查询幂等 token、按订单 ID 锁定/条件取消、插入和计数 | `reservation_order`、`UNIQUE(active_listing_id)` |

类图的三条实体关联与数据库三条 FK 对应：**UserAccount 1 — 0..N BookListing（发布）；UserAccount 1 — 0..N ReservationOrder（购买）；BookListing 1 — 0..N ReservationOrder（历史订单）**。每条订单只属于一个买家和一本书；BookListing 可存在 0 条或多条**历史**订单，但同时**有效订单至多 1 条**（由数据库生成列唯一键提供额外兜底）。

### 1.1 状态与派生值

- `ListingStatus = {可售, 已预留}`，由书籍状态字段表示。它属于**跨表受控冗余**，单独改这一字段不能保证订单状态一致。
- `OrderStatus = {有效, 已取消}`；订单一旦取消就保持已取消并保留历史。重新预留必须生成新的 `orderId`，不能恢复旧订单。
- `ReservationOrder./activeListingId: Long?` 是**只读派生值**：订单有效时等于 `listingId`，取消时为 `null`；写数据库时由生成列维护。斜杠 `/` 是 UML 派生属性标记，不代表独立外键。
- `UserAccount.accountCode` 必填且唯一；`BookListing.price` 是 Decimal，原始输入小数位 **>2** 必须先拒绝，不可依赖数据库舍入；发布日期、下单时间由数据库默认值填写，不能让卖家/买家任意传值或修改。

## 2. 主要操作契约与输入/输出

| 所属类／方法 | 输入 | 正常输出 | 失败处理／依赖 |
|---|---|---|---|
| `ReservationController.issueRequestToken` → `ReservationService.issueRequestToken` | 经认证的预置用户 `buyerId: Long` | `UUIDString`，规范 36 字符 UUID，用于**即将开始的下单动作**；在首个下单请求发出前向客户端提供 | 身份无效拒绝。此为技术准备方法，**不是新独立业务用例**；实际服务端尚未实现 |
| `ReservationController.reserveBook` | `buyerId: Long`、`listingId: Long`、`requestToken: UUIDString` | `ReservationResult{orderId, listingId, orderStatus, replayed}` | 仅委托 Service，不直接插入订单；映射业务拒绝原因 |
| `ReservationService.placeReservation` | 同上 | 新单：一笔有效订单＋书已预留，`replayed=false`；同动作重试：原 `orderId` **当前状态**，`replayed=true` | 必须同一事务控制书和订单，见 §3；买家无效/书不存在/自购/已预留/token 跨书/竞争等均拒绝且不产生半完成数据 |
| `ReservationController.cancelReservation` → `ReservationService.cancelReservation` | `buyerId: Long`、**具体 `orderId: Long`** | `CancelResult{orderId, orderStatus='已取消'}` | 无单/非本人/旧单或重复取消则拒绝，不改变新订单与书籍 |
| `ReservationOrder.markCancelled` | `dbNow: DateTime` | 仅对象仍“有效”时把内存状态置为“已取消”、写入取消时刻；返回 `void` | **已取消时抛领域状态错误 `ORDER_NOT_ACTIVE`，不返回 false、不覆盖旧 `cancelledAt`；非法时间拒绝且不改对象**；本方法不执行 SQL |
| `ReservationOrderRepository.cancelIfActive` | `orderId, buyerId, dbNow` | **`Int` 更新行数，正常范围 0 或 1；恰好 1 才说明条件更新成功** | `WHERE order_id=? AND buyer_id=? AND order_status='有效'`；0 表示未修改，Service 依锁内状态区分订单不存在/越权/重复取消；非预期行数或 SQL 异常回滚 |
| `BookListingRepository.lockById` | `listingId` | 锁内当前 `BookListing` 或 null | 用于同一事务内后续检查/更新，失配则不插入订单 |
| `ReservationOrderRepository.findByBuyerAndToken` | `buyerId, token` | 已有 `ReservationOrder?` | 重放命中必须对比 `listingId`，不能简单把不同书籍误判为成功 |

**参数及返回属于设计接口**，尚未确定 Java 方法签名、HTTP 状态码或 UI 风格。上述 `Result/Error` 不新增数据库 `order_status` 取值。

## 3. `placeReservation` 的关键流程（UC-04）

1. **请求前准备**：服务已通过 `issueRequestToken(buyerId)` 签发并交客户端保存本次逻辑下单动作的 UUID。新动作生成新 token，同动作断线重试复用原 token。服务端需校验 UUID 的规范格式；仅数据库 `CHAR(36)` / `UNIQUE` 不足以保证它是有效 UUID。
2. 接到 `placeReservation(buyerId, listingId, token)`，从可信会话确定账号身份并经 `users.findById` 核对；根据 `orders.findByBuyerAndToken` 先排查同一买家是否已用相同 token。命中时**先比对原单 `listingId`**：同书返回原订单当前状态；不同书拒绝 `TOKEN_TARGET_MISMATCH`，不得创建订单。
3. 对新动作开启事务，`books.lockById(listingId)` 取得目标书的行锁；书存在后先使用当前读或等效机制再次核查相同 token，命中则先处理同书重放/跨书拒绝，结束本次事务且不写入。只有未命中才校验书可售且 `buyerId != sellerId`（R-04），并检查该书没有有效订单。
4. `orders.insert(order)` 插入有效订单，其 `requestToken` 是已验证且复用规则正确的 UUID、`placedAt` 由 DB 默认值产生；数据库用 `UNIQUE(active_listing_id)` 兜底同书有效订单最多 1 条，并用 `UNIQUE(buyer_id,request_token)` 兜底幂等。
5. `books.updateAvailability(listingId,已预留)`；**订单插入与书籍状态更新同一事务成功提交后**再返回 `ReservationResult`。中途出错完整回滚，不能留下“书已预留但无订单”等半完成状态。
6. 竞争/唯一键冲突或死锁时不直接宣称成功：先回滚失败事务，在新的事务/可用读取上下文中重新查询 token 与目标书身份，按以下明确的安全重试规则反馈。重复/跨书请求的语义与并发执行不能只靠单列外键或前端判断。

**安全重试（v0.3）**：同一逻辑下单动作的网络重试、死锁或暂时性故障重试必须复用原 token，不得自动生成新 token；仅用户明确发起全新逻辑动作才签发新 token。唯一冲突先回滚，再用新的读取上下文查询买家+token，命中同书返回原订单的当前状态（含已取消），命中跨书返回 `TOKEN_TARGET_MISMATCH`；token 未命中且同书存在其他有效订单（包括同买家不同 token 的竞争）返回 `ALREADY_RESERVED`。未确认结果的暂时性错误可提示原 token 重试，不承诺一定成功。

**补充技术前提**：若数据库在 `REPEATABLE READ` 下已有一致性快照，获锁后再次使用普通快照查询未必能看见其他事务新提交的 token。生成列/组合 UNIQUE 仍是写入兜底；冲突后**必须回滚并新事务查询**，不能沿用可能过时的快照伪造“没有重试命中”。这是设计责任分工，并非实测结论。

### 3.1 `placeReservation` 错误与数据保证

| 触发条件 | 错误类型（建议） | 数据保证 |
|---|---|---|
| 身份未确认、UUID 非法、书籍不存在 | `INVALID_USER / INVALID_TOKEN / LISTING_NOT_FOUND` | 不新增订单、不改书状态 |
| 目标书已预留 | `ALREADY_RESERVED` | 原有效订单与书状态保持不变 |
| 请求者是书的发布者 | `SELF_RESERVATION` | 无自购记录；书保持原状态 |
| 相同 token 用于不同书籍 | `TOKEN_TARGET_MISMATCH` | 不返回别的书的订单为成功；不生成新订单 |
| 同一逻辑请求重试（包括旧单已取消） | `EXISTING_RESULT` | 返回原 `orderId` 的**当前**状态，不新建新单、不会复活旧单 |
| 两名买家竞争或写入异常 | `CONCURRENT_CONFLICT / SYSTEM_FAILURE` | 同书有效订单≤1，失败事务不留部分状态；暂时性故障重试须复用原 token；只有全新逻辑动作才使用新 token；确认目标已被其他有效订单占用时返回 ALREADY_RESERVED |

## 4. `cancelReservation` 的关键流程（UC-05）

1. Controller 接收**具体订单号 `orderId`** 与当前经过会话认证的买家，不能只按书号取消。Service 可先按 `orders.findById(orderId)` 获取目标 `listingId`，该关联在订单记录建立后视为不可变。
2. 开启事务，**先锁定相应的 BookListing 行**（统一锁顺序），再通过 `orders.lockById(orderId)` 读取并锁定原单；核验当前请求买家 `buyerId == order.buyerId` 且 `orderStatus=='有效'`，否则不修改任何订单和书状态。
3. 用**数据库时钟** `NOW(6)`（建议所有业务连接统一会话 UTC）获取 `dbNow`；通过 `orders.cancelIfActive(orderId,buyerId,dbNow)` 做一次条件更新。要求影响行数正好为 1，且 `dbNow >= placedAt`，并保证 `cancelledAt` 非空、`activeListingId` 派生 NULL。
4. 在同一事务内核对该书是否还有有效订单；如无，则 `books.updateAvailability(listingId,可售)`。保留已取消 O1 的历史；如后来新建 O2，O1 的重复取消不能影响 O2。
5. 提交成功后返回取消结果。异常、数据库时间不满足先后约束、权限不通过或状态不满足时拒绝并完整回滚；不允许取消“他人的订单”、重复取消“已取消订单”，也不能把原订单状态恢复为“有效”。

**数据库与应用边界**：`cancelled_at >= placed_at` 由 CHECK 作为数据库层兜底；`placed_at` / `published_at` 的 `DEFAULT CURRENT_TIMESTAMP(6)` 只有**省略列时**才自动填，不能阻止有足够权限的 SQL 显式修改，必须靠服务白名单/最小权限等软件设计保护。真正的 MySQL SQL/事务/并发测试**尚未执行**。

### 4.1 `cancelReservation` 错误与数据保证

| 条件 | 结果 | 不变量 |
|---|---|---|
| 无该订单号 | `ORDER_NOT_FOUND` | 任意书/订单都不改 |
| `buyerId != order.buyerId` | `FORBIDDEN_CANCEL` | 原单及书不改、不能泄露他人隐私 |
| 订单已取消/旧请求重放 | `ORDER_NOT_ACTIVE` | 旧 O1 不影响新 O2；历史继续保留 |
| 更新行数 != 1／数据库异常 | `SYSTEM_FAILURE` 或安全拒绝 | 回滚未提交的书/订单更新，不产生部分状态 |
| 成功取消 | `CANCELLED` | 原单已取消、留历史、书状态只按实际有效订单维护 |

## 4.2 对 C 在 #14 的三项审阅建议的统一答复（2026-11-24）

> 本小节为 A 负责部分的设计契约补充。C 已于 [#14 交付评论](https://github.com/LianOldMan/se-software243-group21/issues/14#issuecomment-7101388147) 给出意见，但仍需 C 在 #12 对修订后的实际文件独立留言确认；这里不能代替 C 的人工复核。

| C 的关注点 | 本版确定的操作契约 | 不变量 |
|---|---|---|
| ReservationService 的事务边界 | **Controller 不开启事务，Repository 不自行提交**。placeReservation 针对新动作在锁书之前开启写事务，锁书→校验及二次 token 核查→插入订单→修改书状态→提交；同 token 已命中时只返回原单当前状态，不重复写入。cancelReservation 在按订单号只读定位目标书后开启事务，**先锁书再锁订单**，校验本人/状态→条件取消→核对剩余有效单→按需更新书状态→提交。任一步失败完整回滚。 | 下单或取消的订单/书籍两表要么一起提交、要么一起不改 |
| markCancelled 的重复取消处理（Q-01） | **保留 void 方法签名，选择抛领域状态异常，不采用 Boolean 返回 false**。要求当前状态“有效”且数据库时刻不早于下单时间；不满足时拒绝并保持对象原样，尤其不可覆盖旧取消时刻。本方法只做实体内存状态变更，不执行 SQL。 | 已取消→已取消不能再次成功 |
| cancelIfActive 的影响行数（Q-02） | **保留 Int 返回值**。带 orderId、buyerId、orderStatus='有效' 的条件更新影响 1 行才代表本次取消更新成功；0 行代表未改动，应由 Service 依据锁内查询区分 ORDER_NOT_FOUND / FORBIDDEN_CANCEL / ORDER_NOT_ACTIVE；非 0/1 行数或 SQL 异常回滚。 | 旧 O1 的请求不能触碰新 O2，也不能仅凭书号取消 |

**对象动作与数据库更新顺序**：Service 锁内取得数据库时刻并校验对象仍有效及买家身份；先调用 cancelIfActive，确认受影响行数为 1 后，对事务上下文中的订单调用 markCancelled(dbNow) 同步内存对象，再核对有效单并维护书籍状态。任一操作失败立即回滚数据库事务并丢弃本次内存变更。**只有整个事务成功提交才返回 CANCELLED**，不能把 SQL 更新一行或内存对象变化当成已提交。

**并发边界**：下单和取消都先锁相应 BookListing，取消随后锁订单以保持顺序。旧 O1 已取消而新 O2 有效时，O1 重复取消在状态守卫处拒绝，既不修改 O2，也不释放书籍。由 UNIQUE(active_listing_id) 和 UNIQUE(buyer_id,request_token) 做数据库最后兜底；遇唯一冲突须先回滚，在新事务或新读取上下文重新查询，再决定幂等返回、跨书 token 冲突或已预留拒绝，不能依赖旧事务的过期快照。

**C 的 Q-05**：Repository 只向 Service 报告唯一约束/数据库异常；**Service 负责回滚后重新读取、分类业务结果**。上述决定对应 [C 的规则文档 v0.1](09_状态与活动规则_v0.1.md) §4 和 §6 Q-01/Q-02/Q-05。C 原始文件不由 A 代改；B/C 已画的图若使用不同签名或事务位置，应在真正复核时同步更正。

## 5. 状态、类图与两类业务的一致性核对

| 核对问题 | 类/操作依据 | 数据库依据 | B/C 建图要点 |
|---|---|---|---|
| 为什么不是每个买家一个独立订单表？ | `ReservationOrder.buyerId` 联系 `UserAccount` | `buyer_id` FK，用户可兼任两个角色 | 不新增 `Buyer` 和 `Seller` 持久化表 |
| 为什么一本书有多条历史订单？ | `BookListing 1 → ReservationOrder 0..N` | `listing_id` FK；有效唯一由生成列 UNIQUE | 协作图和状态图不能把全部历史误写 1:1 |
| 什么方法负责同一书的预留并发？ | `placeReservation` + `lockById` + `insert` | `UNIQUE(active_listing_id)` | 顺序图显示锁/事务；异常分支解释竞争拒绝 |
| 什么方法负责取消旧订单？ | `cancelReservation` + `cancelIfActive` | `order_id`、`buyer_id`、`order_status`、时间 CHECK | 状态图只允许有效→已取消；活动图不得释放新单 |
| 同一 token 重试返回什么？ | `findByBuyerAndToken` + 校验 `listingId` | `UNIQUE(buyer_id,request_token)` | 同书返回旧订单**当前状态**；跨书 token 拒绝 |
| 为何书的可售状态不是独立真相？ | Service 维护两表状态，单表 `isAvailable` 仅供局部判断 | `availability_status` 为受控冗余 | 只对提交后稳定状态断言一致，事务中间态不能当最终结果 |
| 六场景能否连贯解释？ | `issueRequestToken/reserveBook/placeReservation/cancelReservation` | 8 FR/5 UC、三表关联 | 3 正常＋3 异常；由 A/B/C **共同**走查，不因绘图不同而改业务规则 |
