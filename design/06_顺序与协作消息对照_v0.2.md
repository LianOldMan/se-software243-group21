## 0. 目的与边界

本文把图 04（顺序图）与图 05（协作图）之间的**对象对应、消息编号对应、方向与返回**逐条写清楚，供 A 检查"消息是否属于类图中的方法"、供 C 核对"状态与流程是否与顺序消息一致"。

- 只使用 v0.3 已确认的类名、方法名、参数与返回类型，不新增方法、不新增实体、不新增状态。
- 两张图是**同一场景的两种表达**，不是一张图复制两次：顺序图按时序展开并含两层 `alt`；协作图按对象连接展开，只画正常路径，异常分支通过编号与图 04 的 `alt` 片段对应。
- 所有参数与返回均取自 v0.3 §2、§3 的方法表；错误码取自 v0.3 §3.1、§4.1。
- **编号以 `01_统一类与操作约定_v0.3.md` §4 的"建议稳定的消息编号"表为准**，本图与之逐条对照，未自行增删层级（核对见 §3.1）。

## 1. 转换方式说明

**转换方式：手工转换（非工具自动生成）。**

对照 A 在 `#13` 中的要求（"从该同一顺序图转换协作图，参与对象、调用方向、消息编号 `1/1.1/...` 与顺序图对应，写出对象及消息对应表与转换方式"），本次采用固定四步：

1. **先定对象集合**：从顺序图的 6 条生命线直接取 6 个对象，不增不减（见 §2）。
2. **先定编号规则**：`1` 为买家到边界的首个请求；`1.1` 为其内部调用；`1.1.n` 为 Service 对 Repository 的调用。**编号在两张图中共用同一套**，顺序图的消息标签与协作图的箭头标签一一对应。返回消息统一用 `«return»` 标注，不参与正向编号。
3. **逐条搬消息**：按顺序图从上到下的次序，把每条消息画到对应两对象的连线上；同一对对象之间有多条消息时（如 `svc—orders` 有 4 条），沿连线依次错开绘制。
4. **逐条回读核对**：核对编号、发送方、接收方、方法名、参数、返回六项在两图中是否完全一致（核对结果见 §8）。

没有使用 draw.io 的自动布局或任何代码生成工具的语义转换；两图的可编辑源（`.drawio`）与阅读图（`.png`/`.svg`）为同一版式。

**编号说明**

- `1.1.3`～`1.1.7` 全部**嵌套在 `1.1` 的调用里**，因此统一使用 `1.1.n` 前缀；这与"Service 是唯一编排者"的类职责一致。
- **"自身校验"不占独立编号。** `book ≠ null ∧ isAvailable() ∧ buyerId ≠ sellerId` 是 Service 在锁内对已取得实体的判断，属于 `alt` 的**守卫条件**，不是一次消息交互；因此它写在图 04 内层 `alt` 的分支守卫里，而不是画成带编号的自调用。这样编号与 01 v0.3 §4 完全对齐，也不引入"Service 给自己发消息"这种在类图中没有对应方法的元素。
- **锁后复查（1.1.4）先于可售/自购判断**，这是 v0.3 明确的顺序（"命中则先处理同书重放/跨书拒绝，结束本次事务且不写入；只有未命中才校验可售与自购"）。图 04 的 `alt` 分支次序按此排列。
- 顺序图中另从前置条件注释说明 `issueRequestToken(buyerId)` 已在下单动作**之前**完成，按 A 的要求**不占用消息编号 1～2**。

## 5. 备选与异常分支在两图中的对应

**外层 `alt`：幂等预查结果（依据 1.1.2 的返回）**

| 分支 | 守卫条件 | 顺序图（图 04） | 协作图（图 05） | 错误码 |
|---|---|---|---|---|
| 同 token 同书 → 幂等重放 | `[existing ≠ null ∧ existing.listingId = listingId]` | 外层 `alt` 第一分支，返回 `replayed = true` | 只画正常路径，此分支不在图中 | `EXISTING_RESULT` |
| 同 token 跨书 → 拒绝 | `[existing ≠ null ∧ existing.listingId ≠ listingId]` | 外层 `alt` 第二分支 | 同上 | `TOKEN_TARGET_MISMATCH` |
| 新逻辑动作 | `[existing = null]` | 外层 `alt` 第三分支（1.1.3 起） | **即本图展开的正常路径** | — |

**内层 `alt`：锁后复查结果（依据 1.1.4 的返回）**

| 分支 | 守卫条件 | 处理 | 协作图表现 | 错误码 |
|---|---|---|---|---|
| 等待锁期间已被同一 token 抢先写入 | `[existing ≠ null]` | **先结束本事务、释放书锁再返回**；同书返回原单 `replayed = true`（含 `orderId` / `listingId` / `orderStatus`）；跨书拒绝 | 不在图中（正常路径为 `null`） | `EXISTING_RESULT` / `TOKEN_TARGET_MISMATCH` |
| 校验不通过 | `[existing = null ∧ (book = null ∨ ¬isAvailable() ∨ buyerId = sellerId)]` | 回滚，不写任何数据 | 同上 | 见下方判定次序 |
| 校验通过 | `[existing = null ∧ book ≠ null ∧ isAvailable() ∧ buyerId ≠ sellerId]` | 继续 1.1.5 | **本图展开的后续路径** | — |

**校验不通过时的错误码判定次序**（图 04 该分支的返回标签按此顺序书写）：

| 优先 | 条件 | 返回 |
|---|---|---|
| 1 | `book = null`（锁后取不到书籍行） | `LISTING_NOT_FOUND` |
| 2 | `buyerId = sellerId`（自购） | `SELF_RESERVATION` |
| 3 | 非自购但 `¬isAvailable()`（书已被预留） | `ALREADY_RESERVED` |

**计数分支 `alt [count = 0]`：1.1.5 返回之后**

| 分支 | 守卫条件 | 处理 | 协作图表现 | 错误码 |
|---|---|---|---|---|
| 同书已有其他有效订单 | `[count > 0]` | 回滚，**不执行 1.1.6 / 1.1.7** | 不在图中 | `ALREADY_RESERVED` |
| 同书无其他有效订单 | `[count = 0]` | 执行 1.1.6 `insert` → 1.1.7 `updateAvailability` → 同事务 commit | **本图展开的后续路径** | — |

> **`ALREADY_RESERVED` 有两个来源**：① 锁后校验发现书不可售（已被预留）；② 1.1.5 计数 `> 0`（含同买家不同 token 的竞争）。两处都不得执行 1.1.6 / 1.1.7。这是本版相对 v0.1 的主要修正（v0.1 错把它只挂在 1.1.5 上）。

### 5.1 唯一键冲突与暂时性故障的分类（新增）

1.1.6 / 1.1.7 / commit 任一步失败，**不得返回成功**。已知失败后按下列次序处理，全程复用原 token，不得自动换新 token：

| 情况 | 处理与返回 |
|---|---|
| 回滚后在新读取上下文按 `(buyerId, token)` 命中、且 `listingId` 相同 | 返回原订单**当前状态**（含已取消），`replayed = true` |
| 命中但 `listingId` 不同 | 拒绝 `TOKEN_TARGET_MISMATCH` |
| 未命中，但同书已有有效订单（含同买家不同 token 的竞争） | 拒绝 `ALREADY_RESERVED` |
| 死锁 / 暂时性故障、结果未确认 | 按 `CONCURRENT_CONFLICT` / `SYSTEM_FAILURE` 反馈；提示可用**原 token** 重试，不承诺一定成功 |

图 04 的 `«commit»` 注释与图 05 说明 ④ 均指向本节，不额外增加调用编号。

**协作图的简化边界**：本图只展开正常路径（1.1.2 与 1.1.4 均未命中 token、1.1.5 的 `count = 0`）。这是通信图的常规简化，不是表达能力限制——通信图可以在消息标签上附加守卫条件来表达分支。本图把分支留在图 04 的 `alt` 片段与本文件 §5 的分支表里，图 05 说明区已注明编号共用、可直接回溯。
