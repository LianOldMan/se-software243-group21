## 0. 结论摘要

1. **检索与查看是只读业务，本身不改变任何状态。** 它们的设计目标不是“能查到”，而是**让买家在提问之前就能判断这本书还能不能买**——这正是项目情境里“书籍是否仍可购买需要反复询问”的痛点。因此“可售状态”必须是检索结果与详情的**必有字段**，不能只在详情页才出现。
2. **UC-02 与 UC-03 是两个并列的用户目标，不是先后步骤。** 检索结果列表本身就要给出足以决策的信息（书名、价格、成色、可售状态）；查看用于获取更完整的书籍信息。按任务单第五节的检查要点，**不因为“先检索后查看”就画 `include`**。
3. **已预留书籍是否出现在检索结果中，是必须回答的问题，不是可以留白的细节。** 本稿建议：**可以出现在结果中，但必须显式标注“已预留”，且下单入口不可用**。理由是让买家获得“这本书暂时买不到”的确定答复，比让它凭空消失更符合业务目标。此项已由共享稿 v0.5.3 第 7 节 **Q-01** 与规则 **R-05** 确认为全组决策：默认展示全部并标注“已预留”，另提供“仅看可售”筛选。本稿原建议被采纳，相关待确认标记已全部撤销。
4. **下单只表示预留，不表示付款。** 下单成功产生一条“有效”订单，书籍由“可售”变为“已预留”；全程不产生任何支付、退款、物流动作（B-04、B-06）。
5. **“同一本书同一时刻最多一个有效订单”是业务不变量，不是一条可选的校验。** 因此并发下单的目标不是“尽量少冲突”，而是**结果层面恰好一个成功**：不允许出现两条有效订单，也不允许出现“书籍显示已预留但没有有效订单”的空挂状态。
6. **检查与创建必须是同一个不可分割的业务判断。** 需求层只约束结果（恰好一个成功、失败方无任何副作用），不规定用锁、唯一索引还是条件更新实现——那是实验二、实验三的事。
7. **同一买家的重复提交不构成第二个订单。** 快速连点或网络重发时，第二次及以后必须失败或被视为同一次预留，不得产生多条有效订单；该结论由不变量 I1 直接推出，不需要新增需求条目。
8. **本稿的 12 条个人问题已按语义对齐共享稿，不再按编号互引。** 全部问题改用 `B-Q-01～B-Q-12` 前缀，与共享稿第 7 节的 `Q-01～Q-08`（已采纳决策）严格分开。经逐条比对，7 条已有共享结论、1 条部分覆盖、4 条仍未覆盖（B-Q-04 检索是否要求登录、B-Q-06 详情字段是否含卖家标识与发布时间、B-Q-11 数据不一致的处理、B-Q-12 同一卖家重复发布），映射见第 11 节的对照表。
9. **原“查看我的订单”缺口已由共享稿闭合：** v0.5.3 的 **Q-06** 规定预留成功后返回订单标识并提供携带该标识的取消入口，FR-05 也把“返回订单标识、结果及取消入口”写进需求正文。因此不需要新增用例，本稿第 11.3 节保留分析过程，结论标记为已解决。

## 1. 分析范围、依据与方法

### 1.1 范围内

- 买家按条件查找书籍（UC-02 / FR-03）。
- 买家查看一本书的信息与可售状态（UC-03 / FR-04）。
- 买家对可售书籍发起下单预留（UC-04 / FR-05）。
- 书籍已被预留时的下单拒绝、两名买家竞争时的业务约束（UC-04 / FR-06）。
- 与上述内容直接相关的候选规则评审（R-02、R-04、R-05 为主）。

### 1.2 范围外

按教师基本约定 B-02、B-06，本阶段不涉及：

- 注册、登录密码找回等账号管理（使用预置测试账号）；
- 真实支付、退款、物流、交易完成、评价、推荐；
- 书籍下架、删除、修改发布信息（教师材料未要求，且会引入新的状态迁移）；
- 卖家侧订单管理、管理员后台；
- 数据库表结构、索引、锁、类方法、接口协议等设计与实现细节；
- “我的订单”列表的完整功能定义（仅作为缺口指出，见 第11.3节）。

> 本稿只描述“业务上应发生什么”和“如何客观检查”。文中出现的“原子判断”“状态一致”等说法是需求层的结果约束，不是要求采用某一种技术方案。

### 1.4 分析方法（五步）

1. **定对象**：把“书籍发布记录”和“订单”当成两个不同的东西。检索与查看只作用于书籍；下单同时作用于书籍与订单。混淆二者是 S-04、S-05 类问题的主要来源。
2. **定状态**：先画出书籍与订单各自的取值集合和允许的迁移，再让每条需求说清“迁移前后是什么状态”。没有状态迁移描述的需求无法验收。
3. **定角色**：判断“谁能下单”用的是账号身份与发布者身份的比较，不是页面上的角色切换。同一账号可以既是买家又是卖家（B-03）。
4. **定结果**：每条需求写成“谁在什么条件下，需要系统做什么，结果是什么”，并配一条“给定—操作—预期”的验收条件。
5. **定边界**：凡教师材料未要求的能力（下架、支付、评价、订单管理）一律不进本稿，宁可列为待确认，也不擅自扩大范围。

## 2. 术语、角色与状态

### 2.1 术语表

| 术语 | 本稿定义 |
| --- | --- |
| 发布记录 | 卖家提交的一条书籍信息，一条记录代表一本实物书（B-03） |
| 可售 | 书籍当前不存在有效订单，可被下单 |
| 已预留 | 书籍当前存在一条有效订单，暂不可被再次下单 |
| 有效订单 | 状态为“有效”的下单记录，代表一次未被取消的预留 |
| 检索条件 | 书名关键词与可选的作者筛选条件 |
| 匹配结果 | 同时满足全部已选条件的发布记录集合 |
| 空白检索 | 未输入任何检索条件即提交检索 |
| 自购 | 买家对本人发布的书籍发起下单 |
| 竞争下单 | 两名不同买家对同一本书几乎同时下单（S-04） |

### 2.2 角色与权限

| 角色 | 可执行的业务 | 说明 |
| --- | --- | --- |
| 买家 | 检索书籍、查看书籍、对可售书籍下单 | 本稿主责角色 |
| 卖家 | 发布书籍；查看自己发布的记录 | 卖家与买家可由同一账号承担（B-03） |
| 兼有身份者 | 既可下别人的单，也可被别人下自己的单 | 唯一被限制的是“对自己发布的书籍下单”，该限制**已由 R-04 确认**（小组自定规则，非教师规定） |

> 角色是业务角色，不是权限实体。本阶段不定义角色表、权限位或登录态实现。

### 2.3 状态与状态机

**书籍发布记录**

```
        （发布成功，UC-01）
                │
                ▼
            ┌───────┐   下单成功（UC-04）   ┌────────┐
            │ 可售  │ ───────────────────▶ │ 已预留 │
            └───────┘ ◀─────────────────── └────────┘
                           取消成功（UC-05）
```

本阶段书籍只有“可售”“已预留”两个状态。交易完成不在范围内（B-06），因此**不存在“已售出”状态**；下架与删除同样不定义。

**订单**

```
   有效 ──取消成功（UC-05）──▶ 已取消（终态，保留历史）
```

**关键结论：** 书籍从“已预留”回到“可售”的**唯一路径**是取消订单。这一点意味着下单与取消共享同一个状态变量，FR-05/FR-06 与 FR-07/FR-08 必须使用同一套状态定义，不能各写一套。

### 2.4 业务不变量

| 编号 | 不变量 | 来源 |
| --- | --- | --- |
| I1 | 同一本书同一时刻至多存在一条有效订单 | B-04 |
| I2 | 书籍状态为“已预留”当且仅当存在一条该书籍的有效订单（双向一致） | 由 I1 与状态机推出 |
| I3 | 订单创建后，其关联书籍与买家不可变更 | 由“预留”语义推出，待全组确认 |
| I4 | 订单记录不物理删除，取消只改变状态 | B-05 |
| I5 | 下单与取消全程不改变任何资金、物流或交易完成状态 | B-04、B-06 |
| I6 | 检索与查看是只读操作，不改变书籍、订单或历史的任何状态 | 本稿提出 |

> I2 是本次最容易出问题的一条：它要求“书籍已预留”和“存在有效订单”永远同时成立。任何只改一方的实现都会在验收时暴露，因此它同时是设计约束和验收依据。

## 3. FR-03 检索书籍分析与修订建议

### 3.1 现有表述

> **FR-03**：买家可按书名关键词检索书籍，并按作者进一步筛选；系统返回符合条件的书籍结果。
> 现有验收方法：给定含不同书名、作者的虚构书籍数据；按书名检索并使用作者筛选；预期返回记录符合指定条件。无匹配时的具体提示文案待确认。

### 3.2 逐项分析

| 序号 | 问题 | 说明 | 建议 |
| --- | --- | --- | --- |
| 1 | 关键词的匹配方式未定义 | “按书名关键词”可以是精确、包含、分词或拼音匹配，四种方式的可验收结果完全不同 | 本阶段已确认**包含匹配**（书名包含关键词即命中）与去除首尾空格；**大小写敏感性尚未被共享规则确定**，忽略大小写仅作个人建议；拼音、分词、模糊纠错列为后续能力 |
| 2 | 作者筛选的匹配方式未定义 | 同上 | 建议同样取**包含匹配**，与书名保持同一套语义，减少用户预期落差 |
| 3 | 多条件组合关系未写 | “书名 + 作者”是同时满足还是任一满足 | 明确为 **AND**（同时满足） |
| 4 | 空白检索行为未定义 | 不填任何条件直接提交时，是拒绝、返回全部，还是返回空 | **已确认**（共享 Q-03）：空条件返回**当前状态筛选下**的全部记录，默认发布时间倒序；不提示“请至少输入一个条件”，空检索等价于浏览 |
| 5 | 结果是否包含已预留书籍未定 | 直接决定“可售状态”字段的意义 | **已确认**（共享 Q-01、R-05）：默认包含并标注状态，另提供“仅看可售”筛选；论证见 第3.4节 |
| 6 | 结果排序未定义 | 影响可用性，也影响验收时“预期顺序”的可判定性 | **已确认**（共享 Q-03）：默认发布时间倒序；**排序也是已确认的功能判据**，验收必须同时检查记录集合与顺序 |
| 7 | 结果为空时的反馈未定义 | 现有表述已标“文案待确认” | **已确认**（共享 FR-03、Q-08）：提示未找到，**保留已输入的条件**，并提供修改或清空条件的入口；不报错、不返回空白页。具体文案措辞仍属个人建议，不作验收依据 |
| 8 | 是否需要登录才能检索未定 | 教师材料只说使用预置测试账号 | **仍未覆盖**（B-Q-04）。共享稿只约定“使用预置测试账号”，未规定检索是否允许匿名；本稿按“检索查看可匿名、下单必须登录”写成软性分支，A4 标为条件成立时才适用 |

> **状态说明**：第 1、2 项已由规则 R-02 确认；第 3 项（多条件 AND）已由 R-02 与 Q-02 确认；第 4～7 项已由 Q-01、Q-03、R-05、Q-08 确认。本稿原以为“待全组表决”的四项，实际在 v0.5.3 中均已定稿，修订时按共享结论改写，不再保留“两种方案”的并列写法。

### 3.3 修订建议（供全组讨论）

**本节不再是“建议”，已按共享稿定稿。** v0.5.3 第 3 节的 FR-03 原文为：

> **FR-03**：买家可以按书名关键词检索书籍，并可按作者筛选，系统返回符合条件的记录；书名和作者去除首尾空格后分别包含匹配，组合取 AND；**空条件返回当前状态筛选下的全部记录，默认发布时间倒序**。**无结果时保留条件并提供修改及清空入口。**

与本稿原建议的差异及处理：

### 3.4 为什么建议“已预留书籍仍出现在结果中”

这是一个需要论证而不是拍板的设计选择，本稿的理由是：

1. **业务目标优先**：项目情境要解决的痛点是“这本书还能不能买需要反复问”。若已预留的书直接从结果里消失，买家无法区分“系统里没有这本书”和“这本书被别人订走了”，仍然要回到群里问。
2. **可检查性更好**：保留记录并标注状态，验收条件可以直接写成“结果中该书状态显示为已预留”，客观可判；而“消失”方案下无法验证检索逻辑是否正确命中。
3. **代价可控**：只需要在结果与详情中显示状态，并在详情禁用下单入口，不引入新状态或新用例。

反过来也存在反对理由（结果看起来“脏”、用户可能误点）。共享稿 v0.5.3 已用 **Q-01** 定稿采纳本建议，并以“仅看可售”筛选化解反对意见——想看干净结果的人可以主动过滤，不需要靠隐藏记录来实现。本稿 B-Q-01 由此转为已确认，不再列为待定。

## 5. FR-05 / FR-06 下单分析与修订建议

### 5.1 现有表述

> **FR-05**：非发布者买家对一条可售书籍成功下单时，系统创建该书籍的有效预留订单，并将书籍状态更新为“已预留”；不发生真实支付。
> **FR-06**：书籍已有有效订单时，系统拒绝新的下单且原订单不变；两名买家竞争预留同一本书时最多一人成功。按已确认的 R-04，用户对自己发布的书籍下单被拒绝。

### 5.2 下单的业务语义

一次成功的下单**同时**产生三件事，缺一不可：

| 序号 | 结果 | 对应不变量 |
| --- | --- | --- |
| 1 | 新建一条状态为“有效”的订单，记录书籍、买家、创建时间 | I1、I3 |
| 2 | 关联书籍状态改为“已预留” | I2 |
| 3 | 向买家返回订单标识与书籍当前状态 | — |

反过来，一次**失败**的下单必须做到：不新建订单、不改书籍状态、不改任何已有订单、返回可理解的原因。这就是“失败后保证”的全部内容。

### 5.3 下单拒绝矩阵

| 编号 | 场景 | 判定依据 | 系统响应 | 状态变化 |
| --- | --- | --- | --- | --- |
| R1 | 未登录或会话失效 | 登录态 | 拒绝，要求登录 | 无 |
| R2 | 书籍不存在或标识非法 | 记录存在性 | 拒绝，提示书籍不存在 | 无 |
| R3 | 书籍当前为“已预留” | 书籍状态 / I1 | 拒绝，提示该书已被预留 | 无 |
| R4 | 下单人是该书籍发布者（自购） | 账号与发布者比较 | 拒绝，提示不能预留自己发布的书籍（**R-04 已确认**，非教师规定，为小组自定规则） | 无 |
| R5 | 同一买家对同一书籍重复提交 | I1 | 除首次外均不产生新订单 | 首次按正常流，其余无变化 |
| R6 | 两名买家几乎同时下单同一本书（S-04） | I1 + 原子判断 | 恰好一人成功；另一人收到“已被其他买家预留”类原因 | 成功方按正常流，失败方无变化 |
| R7 | 书籍显示可售但已存在有效订单（数据不一致） | I2 | 拒绝并记录异常，转待确认处理，不擅自修正 | 无（待定） |
| R8 | 下单过程中发生中断或失败 | I2 | 不得留下“有订单但书仍可售”或“书已预留但无订单”的中间态 | 回到下单前状态 |

### 5.4 竞争下单（S-04）为什么是需求问题而不是实现问题

需求层要回答的只有一句：**结果上必须恰好一个成功**。但这句话要成立，需要写清三个可检查的推论，否则验收时无法判定：

1. **不能“先查后写”**：如果系统先查到“可售”，再单独写订单，两步之间的间隙足以让第二名买家也通过检查。这不是技术选型问题，而是“业务判断必须原子”的需求约束。
2. **失败方必须收到具体原因**：不是“下单失败”，而是“该书已被其他买家预留”。原因可读性直接对应 NFR 中的易用性要求（与 C 负责的 NFR 交叉，不重复计数）。
3. **刷新后状态必须一致**：失败方重新查看该书时，应看到“已预留”，且能看到当前有效订单已不属于自己。若失败方刷新后仍看到“可售”，说明 I2 被破坏。

> 本稿不规定用唯一约束、行锁还是条件更新实现上述约束；实验二、实验三再讨论。此处只要求结果可验收。

### 5.5 重复提交（R5）与并发（R6）的区别

两者容易被合并成一条，但业务含义不同：

- **R5 是同一买家的重复动作**：双击、刷新重发、网络重试。用户并没有“抢”，只是动作重复。合理处理是只认第一次，后续视为无操作或提示“你已预留该书”。
- **R6 是两名不同买家的竞争**：涉及公平性，必须恰好一人成功，且失败方明确知道书被别人拿走了。

验收时应分别构造，不能用一次并发测试同时覆盖两者。

### 5.6 修订建议（供全组讨论）

- **FR-05（修订）**：买家对一条“可售”书籍提交下单时，系统在**同一次判断**中确认该书不存在有效订单且买家符合下单条件，随后创建一条“有效”订单并将书籍状态改为“已预留”。下单不涉及任何支付、资金或物流动作。
- **FR-06（修订，拆为两条）**：
  - **FR-06**：当书籍已存在有效订单时，系统拒绝新的下单，原有效订单与书籍状态均不变；同一买家对同一书籍的重复提交不产生第二条有效订单；两名买家竞争时，结果**恰好一人成功**，失败方收到明确原因。
  - **FR-06a（已由 R-04 确认，不再是候选）**：用户不得对本人发布的书籍下单。依据 **R-04**，该规则已于 2026-11-02 由全组确认为**已确认规则**（共享稿 v0.5.3 第 2 节状态列为“已确认”，第 7 节 **Q-04** 同步为“禁止预留自己发布的书”）。需要保留的边界说明是：这是**小组自定规则，不是教师原定要求**——教师材料把“能否购买自己发布的书”列为未给定细节，小组选择禁止，理由是不限制则卖家可自购占用书籍、形成“自己下单自己取消”的空转，并使取消用例出现“买家=卖家”的身份歧义。规则已确认，但依据性质仍须如实标注。

## 6. UC-02 检索书籍用例描述

### 6.1 基本信息

| 项目 | 内容 |
| --- | --- |

| 用例名称 | 检索书籍 |
| 目标 | 买家按书名与作者条件（可为空）找到可能满足需求的书籍记录，并直接判断其是否可下单 |
| 主要参与者 | 买家 |

| 验收条件 | AC-02-1～AC-02-9 |

### 6.2 主成功流

1. 买家在检索区输入书名关键词与作者（**均可为空**）。
2. 买家选择状态筛选：默认“全部”，可切换为“仅看可售”。
3. 买家提交检索。
4. 系统规范化输入（去除首尾空格）。
5. 系统按“书名包含关键词”且（若填写）“作者包含关键词”筛选发布记录（AND）。
6. 系统按第 2 步的状态筛选过滤：默认保留“可售”与“已预留”，选择仅看可售时只保留“可售”。
7. 若过滤后无任何记录，转异常流 A2。
8. 系统按发布时间倒序返回结果集合，每条显示书名、价格、成色、可售状态。
9. 系统展示结果数量；用例结束。

> 空条件不走单独分支：不填条件时第 5 步的筛选条件恒真，等价于返回当前状态筛选下的全部记录。这正是共享稿 Q-03 的结论，本版不再保留“提示至少输入一个条件”的并列写法。

| --- | --- | --- | --- | --- |
| A1 | 第 3 步，书名与作者均为空（空白检索） | 不视为错误：按当前状态筛选返回全部记录，默认发布时间倒序；不提示“请至少输入一个条件” | 无 | 继续第 8 步返回结果 |
| A2 | 第 7 步，过滤后无匹配记录 | 提示“未找到符合条件的书籍”；**保留已输入的书名、作者与状态筛选**，并提供修改或清空条件的入口；不报错、不显示空白页 | 无 | 用户修改条件后回到第 3 步，或结束 |
| A3 | 第 4 步，关键词含特殊字符或超长（如脚本片段） | 按普通文本处理，不执行、不报错；超长时截断或提示 | 无 | 继续第 5 步 |

### 6.4 业务规则

- **BR-01**：检索是只读操作，不改变书籍、订单或历史状态（I6）。
- **BR-02**：多条件之间为 AND 关系。
- **BR-03**：匹配方式为包含匹配，去除首尾空格（本阶段约定的最小语义，可放宽不可收紧）。忽略大小写是本稿补充约定，共享稿未明写，因此只作实现建议，不单独设验收项。
- **BR-04**：结果必须包含“可售状态”，不得只在详情中展示。
- **BR-05**：用例图中 UC-02 与 UC-03 为并列用户目标，不建立 `include` / `extend` 关系。

## 8. UC-04 下单用例描述

### 8.1 基本信息

| 项目 | 内容 |

| 用例编号 | UC-04 |
| 用例名称 | 下单 |
| 目标 | 买家预留一本当前可售的书籍，形成一条有效订单，使该书在预留期间不再被他人下单 |
| 主要参与者 | 买家 |

| 成功后置条件 | 新建一条“有效”订单；书籍状态为“已预留”；返回订单标识与书籍当前状态；无任何支付动作 |
| 失败后保证 | 不新建订单；书籍状态不变；已有订单不变；返回可理解的原因 |
| 关联需求 | FR-05、FR-06、FR-06a（候选）；B-03、B-04、B-06；R-04；S-03、S-04 |

> 注：本用例旧编号 `AC-05-1～AC-05-10` 已统一为 `AC-B-04-1～AC-B-04-12`，旧号不再使用；新增的 `AC-B-04-5`、`AC-B-04-6` 对应本轮审查建议的候选条目。

### 8.2 主成功流

1. 买家在书籍详情中选择下单。
2. 系统确认买家处于登录状态。
3. 系统按书籍标识读取该书当前状态。
4. 系统在同一业务判断中确认：该书不存在有效订单、状态为“可售”、买家符合下单条件。
5. 判断通过，系统创建一条“有效”订单，记录书籍、买家与创建时间。
6. 系统将该书状态改为“已预留”。
7. 系统向买家展示订单标识、书籍名称与“已预留”状态，并说明此为预留而非付款。
8. 用例结束。

> 第 4、5、6 步在业务上必须构成一个不可分割的整体：不允许在第 4 步与第 5 步之间让其他买家的下单通过检查（对应 第5.4节）。

| A5 | 第 4～5 步，同一买家重复提交，且首次请求已成功（含首次结果未送达、买家重试的情形） | 仅首次生效；其余提示“你已预留该书”或视为同一次预留，不新建订单，不得把已成功的订单判为失败 | 首次按正常流；其余无变化 | 重复请求结束；首次成功请求进入第 7 步 |

### 8.4 业务规则

### 11.3 历史跨材料缺口：取消订单如何定位（现已解决）

UC-05 取消订单的前置条件写的是“买家能定位自己的订单并找到取消入口”，但当前用例图（`软件243_21组_实验一_完整用例图_v0.1.drawio`）只有 UC-01～UC-05 五个用例，没有“查看我的订单”。在共享需求尚未明确订单入口的早期讨论中，这带来两个潜在问题（**现已通过共享 FR-05、Q-06 解决**）：

**当前已确认的结论（共享 v0.5.4，FR-05、Q-06）**：下单成功后，系统返回订单标识、预留结果和**携带该订单标识的取消入口**，买家由此定位订单并发起一次确认后取消；本实验不新增“查看我的订单”独立用例，完整用例图仍为 UC-01～UC-05。上段仅保留最初发现缺口的论证过程，**不再标记为待组长确认**。

## 附录 A 术语与编号一致性

| 项 | 统一用法 | 避免 |
| --- | --- | --- |
| 用例名称 | 检索书籍 / 查看书籍 / 下单 | 检索与查看（合成一个）、预定、购买、抢单 |
| 状态词 | 可售 / 已预留 | 在售、空闲、锁定、已下单 |
| 订单状态 | 有效 / 已取消 | 进行中、完成、作废 |
