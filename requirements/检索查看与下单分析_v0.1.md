## 0. 结论摘要

1. **检索与查看是只读业务，本身不改变任何状态。** 它们的设计目标不是“能查到”，而是**让买家在提问之前就能判断这本书还能不能买**——这正是项目情境里“书籍是否仍可购买需要反复询问”的痛点。因此“可售状态”必须是检索结果与详情的**必有字段**，不能只在详情页才出现。
2. **UC-02 与 UC-03 是两个并列的用户目标，不是先后步骤。** 检索结果列表本身就要给出足以决策的信息（书名、价格、成色、可售状态）；查看用于获取更完整的书籍信息。按任务单第五节的检查要点，**不因为“先检索后查看”就画 `include`**。
3. **已预留书籍是否出现在检索结果中，是必须回答的问题，不是可以留白的细节。** 本稿建议：**可以出现在结果中，但必须显式标注“已预留”，且下单入口不可用**。理由是让买家获得“这本书暂时买不到”的确定答复，比让它凭空消失更符合业务目标。此项为**待确认**，须全组表决后才写入需求。
4. **下单只表示预留，不表示付款。** 下单成功产生一条“有效”订单，书籍由“可售”变为“已预留”；全程不产生任何支付、退款、物流动作（B-04、B-06）。
5. **“同一本书同一时刻最多一个有效订单”是业务不变量，不是一条可选的校验。** 因此并发下单的目标不是“尽量少冲突”，而是**结果层面恰好一个成功**：不允许出现两条有效订单，也不允许出现“书籍显示已预留但没有有效订单”的空挂状态。
6. **检查与创建必须是同一个不可分割的业务判断。** 需求层只约束结果（恰好一个成功、失败方无任何副作用），不规定用锁、唯一索引还是条件更新实现——那是实验二、实验三的事。
7. **同一买家的重复提交不构成第二个订单。** 快速连点或网络重发时，第二次及以后必须失败或被视为同一次预留，不得产生多条有效订单；该结论由不变量 I1 直接推出，不需要新增需求条目。
8. **本稿提出 12 个待确认问题（Q-01～Q-12）**，其中 Q-01（已预留书籍是否出现在结果中）、Q-03（空白检索）、Q-05（能否自购）会直接影响 FR 措辞，建议优先在第二次课定稿前解决。
9. **一处跨材料缺口需要全组处理：** 用例图与需求简表都没有“查看我的订单”这一用户目标，但 UC-05 取消订单默认买家能看到自己的订单并找到取消入口。若不在图中体现，取消用例的前置条件在材料上无处落地（见 §11.3）。
10. **一处提交合规风险：** 当前仓库为 `private: false`（公开），与指导书第十节“创建私有仓库”“不自行公开仓库”不一致（见 §12.4）。

### 1.4 分析方法（五步）

1. **定对象**：把“书籍发布记录”和“订单”当成两个不同的东西。检索与查看只作用于书籍；下单同时作用于书籍与订单。混淆二者是 S-04、S-05 类问题的主要来源。
2. **定状态**：先画出书籍与订单各自的取值集合和允许的迁移，再让每条需求说清“迁移前后是什么状态”。没有状态迁移描述的需求无法验收。
3. **定角色**：判断“谁能下单”用的是账号身份与发布者身份的比较，不是页面上的角色切换。同一账号可以既是买家又是卖家（B-03）。
4. **定结果**：每条需求写成“谁在什么条件下，需要系统做什么，结果是什么”，并配一条“给定—操作—预期”的验收条件。
5. **定边界**：凡教师材料未要求的能力（下架、支付、评价、订单管理）一律不进本稿，宁可列为待确认，也不擅自扩大范围。

## 2. 术语、角色与状态

### 2.1 术语表

| 术语 | 本稿定义 |
| --- | --- |
| 发布记录 | 卖家提交的一条书籍信息，一条记录代表一本实物书（B-03） |
| 可售 | 书籍当前不存在有效订单，可被下单 |
| 已预留 | 书籍当前存在一条有效订单，暂不可被再次下单 |
| 有效订单 | 状态为“有效”的下单记录，代表一次未被取消的预留 |
| 检索条件 | 书名关键词与可选的作者筛选条件 |
| 匹配结果 | 同时满足全部已选条件的发布记录集合 |
| 空白检索 | 未输入任何检索条件即提交检索 |
| 自购 | 买家对本人发布的书籍发起下单 |
| 竞争下单 | 两名不同买家对同一本书几乎同时下单（S-04） |

### 2.2 角色与权限

| 角色 | 可执行的业务 | 说明 |
| --- | --- | --- |
| 买家 | 检索书籍、查看书籍、对可售书籍下单 | 本稿主责角色 |
| 卖家 | 发布书籍；查看自己发布的记录 | 卖家与买家可由同一账号承担（B-03） |
| 兼有身份者 | 既可下别人的单，也可被别人下自己的单 | 唯一被限制的是“对自己发布的书籍下单”，且该限制目前是**暂定**（R-04） |

> 角色是业务角色，不是权限实体。本阶段不定义角色表、权限位或登录态实现。

### 2.3 状态与状态机

**书籍发布记录**

```
        （发布成功，UC-01）
                │
                ▼
            ┌───────┐   下单成功（UC-04）   ┌────────┐
            │ 可售  │ ───────────────────▶ │ 已预留 │
            └───────┘ ◀─────────────────── └────────┘
                           取消成功（UC-05）
```

本阶段书籍只有“可售”“已预留”两个状态。交易完成不在范围内（B-06），因此**不存在“已售出”状态**；下架与删除同样不定义。

**订单**

```
   有效 ──取消成功（UC-05）──▶ 已取消（终态，保留历史）
```

**关键结论：** 书籍从“已预留”回到“可售”的**唯一路径**是取消订单。这一点意味着下单与取消共享同一个状态变量，FR-05/FR-06 与 FR-07/FR-08 必须使用同一套状态定义，不能各写一套。

### 2.4 业务不变量

| 编号 | 不变量 | 来源 |
| --- | --- | --- |
| I1 | 同一本书同一时刻至多存在一条有效订单 | B-04 |
| I2 | 书籍状态为“已预留”当且仅当存在一条该书籍的有效订单（双向一致） | 由 I1 与状态机推出 |
| I3 | 订单创建后，其关联书籍与买家不可变更 | 由“预留”语义推出，待全组确认 |
| I4 | 订单记录不物理删除，取消只改变状态 | B-05 |
| I5 | 下单与取消全程不改变任何资金、物流或交易完成状态 | B-04、B-06 |
| I6 | 检索与查看是只读操作，不改变书籍、订单或历史的任何状态 | 本稿提出 |

> I2 是本次最容易出问题的一条：它要求“书籍已预留”和“存在有效订单”永远同时成立。任何只改一方的实现都会在验收时暴露，因此它同时是设计约束和验收依据。

## 3. FR-03 检索书籍分析与修订建议

### 3.1 现有表述

> **FR-03**：买家可按书名关键词检索书籍，并按作者进一步筛选；系统返回符合条件的书籍结果。
> 现有验收方法：给定含不同书名、作者的虚构书籍数据；按书名检索并使用作者筛选；预期返回记录符合指定条件。无匹配时的具体提示文案待确认。

### 3.2 逐项分析

| 序号 | 问题 | 说明 | 建议 |
| --- | --- | --- | --- |
| 1 | 关键词的匹配方式未定义 | “按书名关键词”可以是精确、包含、分词或拼音匹配，四种方式的可验收结果完全不同 | 本阶段取**包含匹配**（书名包含关键词即命中），不区分大小写，去除首尾空格；拼音、分词、模糊纠错列为后续能力 |
| 2 | 作者筛选的匹配方式未定义 | 同上 | 建议同样取**包含匹配**，与书名保持同一套语义，减少用户预期落差 |
| 3 | 多条件组合关系未写 | “书名 + 作者”是同时满足还是任一满足 | 明确为 **AND**（同时满足） |
| 4 | 空白检索行为未定义 | 不填任何条件直接提交时，是拒绝、返回全部，还是返回空 | 待确认（Q-03）。本稿倾向：允许空白检索并返回全部可售记录，理由是校园场景书目量小，空检索等价于“浏览”；若采用拒绝方案，则必须给出“请至少输入一个条件”的明确提示 |
| 5 | 结果是否包含已预留书籍未定 | 直接决定“可售状态”字段的意义 | 待确认（Q-01）。本稿建议包含并标注状态，论证见 §3.4 |
| 6 | 结果排序未定义 | 影响可用性，也影响验收时“预期顺序”的可判定性 | 建议按发布时间倒序；验收只校验“集合正确”，不校验顺序，避免把排序变成隐含需求 |
| 7 | 结果为空时的反馈未定义 | 现有表述已标“文案待确认” | 明确：返回“未找到符合条件的书籍”，**不报错、不返回空白页**；文案具体措辞待定 |
| 8 | 是否需要登录才能检索未定 | 教师材料只说使用预置测试账号 | 待确认（Q-04）。建议检索与查看允许在未登录状态进行，下单必须登录；若全组不同意，则统一要求登录 |

### 3.3 修订建议（供全组讨论）

建议将 FR-03 拆为一条主需求加一条边界需求，避免把异常塞进同一条里：

- **FR-03（修订）**：买家可按书名关键词检索书籍，并可选按作者进一步筛选；多个条件同时生效（AND）。系统返回满足全部条件的发布记录集合，**每条结果至少显示书名、价格、成色与可售状态**。
- **FR-03a（新增候选）**：当检索条件无匹配记录时，系统明确提示“未找到符合条件的书籍”，不返回空白页或错误页；该提示不改变任何数据。

### 3.4 为什么建议“已预留书籍仍出现在结果中”

这是一个需要论证而不是拍板的设计选择，本稿的理由是：

1. **业务目标优先**：项目情境要解决的痛点是“这本书还能不能买需要反复问”。若已预留的书直接从结果里消失，买家无法区分“系统里没有这本书”和“这本书被别人订走了”，仍然要回到群里问。
2. **可检查性更好**：保留记录并标注状态，验收条件可以直接写成“结果中该书状态显示为已预留”，客观可判；而“消失”方案下无法验证检索逻辑是否正确命中。
3. **代价可控**：只需要在结果与详情中显示状态，并在详情禁用下单入口，不引入新状态或新用例。

反过来也存在反对理由（结果看起来“脏”、用户可能误点），所以此项**必须由全组表决**，不能由本稿单方面定为规则（Q-01）。

### 3.5 FR-03 验收要点

| 编号 | 验收条件（给定—操作—预期） |
| --- | --- |
| AC-03-1 | 给定多条书名不同的虚构记录；输入某本书名的完整关键词检索；预期结果包含该书，且不包含书名不含该关键词的记录 |
| AC-03-2 | 给定书名相同但作者不同的两条记录；以书名关键词 + 其中一位作者筛选；预期只返回该作者对应的那一条 |
| AC-03-3 | 给定关键词命中的记录既有可售也有已预留（若 Q-01 采纳建议）；检索后预期两条都出现，且状态字段分别为“可售”“已预留” |
| AC-03-4 | 输入不区分大小写的关键词（如英文书名）；预期匹配结果与大小写一致时相同 |
| AC-03-5 | 输入首尾带空格的关键词；预期结果与去空格后一致 |
| AC-03-6 | 输入必然无匹配的关键词；预期显示“未找到符合条件的书籍”类提示，页面无报错，数据不变 |
| AC-03-7 | 空白条件提交（按 Q-03 结论）；预期符合所选方案：返回全部可售记录，或提示至少输入一个条件 |
| AC-03-8 | 检索前后对比书籍与订单数据；预期无任何字段变化（I6） |

> 以上均为拟定检查方法，未执行。

## 4. FR-04 查看书籍分析与修订建议

### 4.1 现有表述

> **FR-04**：用户可查看检索结果中的书籍信息，至少获知书名、价格、成色及可售状态；详情展示的其他字段由小组后续确认。
> 现有验收方法：给定一条可售的虚构书籍；查看匹配结果及书籍信息；预期展示字段与实际记录一致。已预留书籍是否也出现在结果中，需全组另行确认。

### 4.2 逐项分析

| 序号 | 问题 | 建议 |
| --- | --- | --- |
| 1 | “查看”的入口未写 | 明确两个入口：检索结果列表项、列表项进入的详情；列表已给最小四字段，详情给完整字段 |
| 2 | 详情字段集合未定 | 最小集沿用 R-05；建议详情增加**卖家标识**与**发布时间**，理由是同一本书可能由不同卖家各发布一本，缺卖家标识无法区分（待确认 Q-06） |
| 3 | 书籍描述、图片是否入库 | 建议列为后续能力，本阶段不写，避免与发布侧 R-01 的必填项冲突 |
| 4 | 已预留书籍的详情行为未定 | 建议：可查看，状态显示“已预留”，下单入口置灰并说明原因；不得出现“能点但下单失败”的静默失败 |
| 5 | 状态一致性 | 详情显示的状态与下单校验使用同一数据来源；但**并发下仍可能出现“页面显示可售、提交时已被他人预留”**，此时按 FR-06 的拒绝路径处理并给出明确原因，不属于展示错误 |
| 6 | 是否需要展示历史订单 | 不属于本用例，超出范围，不写 |

### 4.3 修订建议（供全组讨论）

- **FR-04（修订）**：用户可查看一条发布记录的详细信息。列表与详情均至少显示书名、价格、成色与可售状态；详情另显示卖家标识与发布时间（**待确认**）。已预留书籍可被查看，但其下单入口不可用，并说明原因。

### 4.4 FR-04 验收要点

| 编号 | 验收条件（给定—操作—预期） |
| --- | --- |
| AC-04-1 | 给定一条可售虚构书籍；从检索结果进入查看；预期展示的书名、价格、成色、状态与记录一致 |
| AC-04-2 | 给定一条已预留书籍；进入查看；预期状态显示“已预留”，下单入口不可用，且有可读的原因说明 |
| AC-04-3 | 分别用两条价格、成色不同的记录查看；预期字段与各自记录一一对应，不发生串数据 |
| AC-04-4 | 查看操作前后对比数据；预期无任何字段变化（I6） |
| AC-04-5 | 查看不存在的记录标识（越界/手改地址，若能构造）；预期提示记录不存在，不报错、不暴露其他记录 |

> AC-04-5 的前提是本阶段界面存在可构造的地址参数；若界面不含该项，则本条件记为不适用，不作为失败。

## 5. FR-05 / FR-06 下单分析与修订建议

### 5.1 现有表述

> **FR-05**：非发布者买家对一条可售书籍成功下单时，系统创建该书籍的有效预留订单，并将书籍状态更新为“已预留”；不发生真实支付。
> **FR-06**：书籍已有有效订单时，系统拒绝新的下单且原订单不变；两名买家竞争预留同一本书时最多一人成功。按暂定规则，用户对自己发布的书籍下单也应被拒绝。

### 5.2 下单的业务语义

一次成功的下单**同时**产生三件事，缺一不可：

| 序号 | 结果 | 对应不变量 |
| --- | --- | --- |
| 1 | 新建一条状态为“有效”的订单，记录书籍、买家、创建时间 | I1、I3 |
| 2 | 关联书籍状态改为“已预留” | I2 |
| 3 | 向买家返回订单标识与书籍当前状态 | — |

反过来，一次**失败**的下单必须做到：不新建订单、不改书籍状态、不改任何已有订单、返回可理解的原因。这就是“失败后保证”的全部内容。

### 5.3 下单拒绝矩阵

| 编号 | 场景 | 判定依据 | 系统响应 | 状态变化 |
| --- | --- | --- | --- | --- |
| R1 | 未登录或会话失效 | 登录态 | 拒绝，要求登录 | 无 |
| R2 | 书籍不存在或标识非法 | 记录存在性 | 拒绝，提示书籍不存在 | 无 |
| R3 | 书籍当前为“已预留” | 书籍状态 / I1 | 拒绝，提示该书已被预留 | 无 |
| R4 | 下单人是该书籍发布者（自购） | 账号与发布者比较 | 拒绝（**暂定**，取决于 Q-05） | 无 |
| R5 | 同一买家对同一书籍重复提交 | I1 | 除首次外均不产生新订单 | 首次按正常流，其余无变化 |
| R6 | 两名买家几乎同时下单同一本书（S-04） | I1 + 原子判断 | 恰好一人成功；另一人收到“已被其他买家预留”类原因 | 成功方按正常流，失败方无变化 |
| R7 | 书籍显示可售但已存在有效订单（数据不一致） | I2 | 拒绝并记录异常，转待确认处理，不擅自修正 | 无（待定） |
| R8 | 下单过程中发生中断或失败 | I2 | 不得留下“有订单但书仍可售”或“书已预留但无订单”的中间态 | 回到下单前状态 |

### 5.4 竞争下单（S-04）为什么是需求问题而不是实现问题

需求层要回答的只有一句：**结果上必须恰好一个成功**。但这句话要成立，需要写清三个可检查的推论，否则验收时无法判定：

1. **不能“先查后写”**：如果系统先查到“可售”，再单独写订单，两步之间的间隙足以让第二名买家也通过检查。这不是技术选型问题，而是“业务判断必须原子”的需求约束。
2. **失败方必须收到具体原因**：不是“下单失败”，而是“该书已被其他买家预留”。原因可读性直接对应 NFR 中的易用性要求（与 C 负责的 NFR 交叉，不重复计数）。
3. **刷新后状态必须一致**：失败方重新查看该书时，应看到“已预留”，且能看到当前有效订单已不属于自己。若失败方刷新后仍看到“可售”，说明 I2 被破坏。

> 本稿不规定用唯一约束、行锁还是条件更新实现上述约束；实验二、实验三再讨论。此处只要求结果可验收。

### 5.5 重复提交（R5）与并发（R6）的区别

两者容易被合并成一条，但业务含义不同：

- **R5 是同一买家的重复动作**：双击、刷新重发、网络重试。用户并没有“抢”，只是动作重复。合理处理是只认第一次，后续视为无操作或提示“你已预留该书”。
- **R6 是两名不同买家的竞争**：涉及公平性，必须恰好一人成功，且失败方明确知道书被别人拿走了。

验收时应分别构造，不能用一次并发测试同时覆盖两者。

### 5.6 修订建议（供全组讨论）

- **FR-05（修订）**：买家对一条“可售”书籍提交下单时，系统在**同一次判断**中确认该书不存在有效订单且买家符合下单条件，随后创建一条“有效”订单并将书籍状态改为“已预留”。下单不涉及任何支付、资金或物流动作。
- **FR-06（修订，拆为两条）**：
  - **FR-06**：当书籍已存在有效订单时，系统拒绝新的下单，原有效订单与书籍状态均不变；同一买家对同一书籍的重复提交不产生第二条有效订单；两名买家竞争时，结果**恰好一人成功**，失败方收到明确原因。
  - **FR-06a（候选，暂定）**：用户不得对本人发布的书籍下单（依据 R-04）。该项为小组候选规则，教师材料未要求，教师材料“能否购买自己发布的书”明确列为**未给定细节**，因此本稿仅作候选，不作为已定规则。

### 5.7 FR-05 / FR-06 验收要点

| 编号 | 验收条件（给定—操作—预期） |
| --- | --- |
| AC-05-1 | 给定买家 A 登录、书籍 X 为“可售”且发布者不是 A；A 下单；预期产生恰好一条有效订单，X 变为“已预留”，全程无支付动作 |
| AC-05-2 | 给定同上条件下单成功后；检查订单记录；预期订单关联的书籍为 X、买家为 A、状态为“有效”，且该订单可被 A 在后续取消用例中定位 |
| AC-05-3 | 给定书籍 X 已被 A 预留；买家 B 对 X 下单；预期被拒绝，X 仍为“已预留”，A 的订单不变，B 未产生任何订单 |
| AC-05-4 | 给定书籍 X 可售；同一买家快速连续提交两次下单；预期只产生一条有效订单，第二次不产生新记录 |
| AC-05-5 | 给定书籍 X 可售；买家 A 与 B 几乎同时下单；预期恰好一人成功、一人失败，有效订单总数 = 1，失败方收到“已被其他买家预留”类原因 |
| AC-05-6 | 承接 AC-05-5；失败方刷新查看 X；预期显示“已预留”，且当前有效订单不属于自己（I2 成立） |
| AC-05-7 | 给定书籍 X 由卖家 S 发布且可售；S 对 X 下单（按 Q-05 结论）；预期若采纳 R-04 则拒绝并说明原因，未采纳则按 AC-05-1 正常创建 |
| AC-05-8 | 给定未登录状态；对任一书籍下单；预期被拒绝并要求登录，数据不变 |
| AC-05-9 | 给定订单创建过程中人为中断（可构造时）；预期不出现“有订单但书仍可售”或“书已预留但无订单”的状态 |
| AC-05-10 | 对同一书籍构造“可售 + 已存在有效订单”的异常数据（若能构造）；预期系统拒绝新下单并记录异常，不产生第二条有效订单 |

> 以上均为拟定检查方法，本阶段不实现程序，无法执行；AC-05-9、AC-05-10 需在实验二、实验三具备可构造条件后再判定是否适用。

## 6. UC-02 检索书籍用例描述

### 6.1 基本信息

| 项目 | 内容 |
| --- | --- |
| 用例编号 | UC-02 |
| 用例名称 | 检索书籍 |
| 目标 | 买家按书名与作者条件找到可能满足需求的书籍记录，并直接判断其是否可下单 |
| 主要参与者 | 买家 |
| 异常参与者 | 无（本用例无越权分支） |
| 触发条件 | 买家在检索区输入条件并提交 |
| 前置条件 | 系统中存在至少一条发布记录；使用预置测试账号（是否允许未登录见 Q-04） |
| 成功后置条件 | 页面展示满足条件的记录集合；**数据无任何变化** |
| 失败后保证 | 原数据不变；给出可读提示，不出现空白页或错误页 |
| 关联需求 | FR-03、FR-03a；B-01、B-03；R-02、R-05；S-02 |
| 验收条件 | AC-03-1～AC-03-8 |

### 6.2 主成功流

1. 买家在检索区输入书名关键词，可选输入作者。
2. 买家提交检索。
3. 系统规范化输入（去除首尾空格、忽略大小写）。
4. 系统按“书名包含关键词”且（若填写）“作者包含关键词”筛选发布记录（AND）。
5. 系统返回匹配集合，每条显示书名、价格、成色、可售状态。
6. 系统展示结果数量。
7. 用例结束。

### 6.3 异常流

| 编号 | 触发条件 | 系统响应 | 状态变化 |
| --- | --- | --- | --- |
| A1 | 关键词为空且作者为空（空白检索） | 按 Q-03 结论：返回全部可售记录，或提示“请至少输入一个条件” | 无 |
| A2 | 无匹配记录 | 提示“未找到符合条件的书籍”，不报错 | 无 |
| A3 | 关键词含特殊字符或超长（如脚本片段） | 按普通文本处理，不执行、不报错；超长时截断或提示 | 无 |
| A4 | 会话失效（若检索要求登录） | 提示重新登录 | 无 |
| A5 | 数据源不可用 | 提示暂时无法检索，建议稍后再试 | 无 |

### 6.4 业务规则

- **BR-01**：检索是只读操作，不改变书籍、订单或历史状态（I6）。
- **BR-02**：多条件之间为 AND 关系。
- **BR-03**：匹配方式为包含匹配，忽略大小写与首尾空格（本阶段约定的最小语义，可放宽不可收紧）。
- **BR-04**：结果必须包含“可售状态”，不得只在详情中展示。
- **BR-05**：用例图中 UC-02 与 UC-03 为并列用户目标，不建立 `include` / `extend` 关系。

## 8. UC-04 下单用例描述

### 8.1 基本信息

| 项目 | 内容 |
| --- | --- |
| 用例编号 | UC-04 |
| 用例名称 | 下单 |
| 目标 | 买家预留一本当前可售的书籍，形成一条有效订单，使该书在预留期间不再被他人下单 |
| 主要参与者 | 买家 |
| 异常参与者 | 其他同时下单的买家（竞争，R6）；书籍发布者本人（自购，暂定 R4） |
| 触发条件 | 买家在书籍详情中选择“下单/预留” |
| 前置条件 | 已登录（预置测试账号）；书籍记录存在且状态为“可售”；该书不存在有效订单；买家不是发布者（**暂定**） |
| 成功后置条件 | 新建一条“有效”订单；书籍状态为“已预留”；返回订单标识与书籍当前状态；无任何支付动作 |
| 失败后保证 | 不新建订单；书籍状态不变；已有订单不变；返回可理解的原因 |
| 关联需求 | FR-05、FR-06、FR-06a（候选）；B-03、B-04、B-06；R-04；S-03、S-04 |
| 验收条件 | AC-05-1～AC-05-10 |

### 8.2 主成功流

1. 买家在书籍详情中选择下单。
2. 系统确认买家处于登录状态。
3. 系统按书籍标识读取该书当前状态。
4. 系统在同一业务判断中确认：该书不存在有效订单、状态为“可售”、买家符合下单条件。
5. 判断通过，系统创建一条“有效”订单，记录书籍、买家与创建时间。
6. 系统将该书状态改为“已预留”。
7. 系统向买家展示订单标识、书籍名称与“已预留”状态，并说明此为预留而非付款。
8. 用例结束。

> 第 4、5、6 步在业务上必须构成一个不可分割的整体：不允许在第 4 步与第 5 步之间让其他买家的下单通过检查（对应 §5.4）。

### 8.3 异常流

| 编号 | 触发条件 | 系统响应 | 状态变化 |
| --- | --- | --- | --- |
| A1 | 未登录或会话失效 | 拒绝，要求登录后重试 | 无 |
| A2 | 书籍不存在或标识非法 | 拒绝，提示书籍不存在 | 无 |
| A3 | 书籍已为“已预留” | 拒绝，提示该书已被预留 | 无 |
| A4 | 买家即发布者本人（自购，暂定） | 拒绝，提示不能预留自己发布的书籍 | 无 |
| A5 | 同一买家重复提交 | 仅首次生效；其余提示“你已预留该书”或视为同一次预留 | 首次按正常流，其余无变化 |
| A6 | 两名买家几乎同时下单（S-04） | 恰好一人成功；失败方提示“该书已被其他买家预留” | 成功方按正常流；失败方无变化 |
| A7 | 书籍显示可售但存在有效订单（数据不一致） | 拒绝并记录异常，转待确认处理，不自行修正数据 | 无 |
| A8 | 创建过程中中断 | 不得留下“有订单但书可售”或“书已预留但无订单”的状态 | 回到下单前状态 |

### 8.4 业务规则

- **BR-09**：下单表示预留，不表示付款（B-04）。
- **BR-10**：同一本书同一时刻至多一条有效订单（I1）。
- **BR-11**：书籍“已预留”与“存在有效订单”必须同时成立（I2）。
- **BR-12**：下单失败不得产生任何部分结果（不新建订单、不改状态）。
- **BR-13**：下单不得改变资金、物流或交易完成相关状态（I5）。
- **BR-14**：不得对本人发布的书籍下单（**暂定**，依据 R-04，教师材料未给定）。

## 10. 候选业务规则评审（R-01～R-05）

### 10.1 评审表

| 规则 | 内容 | 成员 B 意见 | 理由与影响 |
| --- | --- | --- | --- |
| R-01 | 发布时书名、作者、价格、成色必填 | **倾向同意，非本人主责** | 与 FR-03 直接相关：书名与作者是检索维度，缺失会使记录无法被检索命中；建议由 A 明确缺失时的反馈 |
| R-02 | 支持书名关键词检索，可按作者筛选 | **同意，需补三点** | 需补：①关键词与作者的匹配方式（建议包含匹配）；②多条件为 AND；③空白检索的处理（Q-03）。不补则 AC-03-1、AC-03-2 无法判定 |
| R-03 | 价格必须大于 0 | **倾向同意，非本人主责** | 与检索结果中的价格展示相关；价格为 0 或负数会让结果出现无意义记录 |
| R-04 | 不允许预留自己发布的书籍 | **建议保留，但降级为“候选”** | 教师材料明确把“能否购买自己发布的书”列为未给定细节，因此它不是教师约定。作为小组自定规则可以成立，但必须写明依据与影响：若不限制，卖家可自购并占用书籍，形成“自己下单自己取消”的空转，也会让取消用例出现“买家=卖家”的身份歧义 |
| R-05 | 检索结果至少显示书名、价格、成色、可售状态 | **同意，建议补一句** | 需补：可售状态的取值集合为“可售/已预留”，且列表与详情必须一致；详情建议增加卖家标识（Q-06） |

### 10.2 跨规则问题

1. **R-02 与 R-05 是同一件事的两半**：一条说“怎么查”，一条说“查到后看到什么”。若分开由不同人写，容易出现“检索条件里没有作者、结果里却要按作者区分”的矛盾。建议合并到同一小节维护。
2. **R-04 会影响 FR-05 的措辞**：现有 FR-05 写的是“非发布者买家”，已经隐含采纳 R-04，但 R-04 本身还是“暂定”。这是当前材料里最需要统一的一处**状态不一致**：需求把暂定规则当成了既定前提。
3. **R-05 的“可售状态”与 I2 绑定**：如果某条记录状态显示错误，问题可能出在取消流程而不是检索流程，验收时要能区分。

### 11.3 跨材料缺口：取消订单依赖“能看到自己的订单”

UC-05 取消订单的前置条件写的是“买家能定位自己的订单并找到取消入口”，但当前用例图（`软件243_21组_实验一_完整用例图_v0.1.drawio`）只有 UC-01～UC-05 五个用例，没有“查看我的订单”。这带来两个后果：

1. **材料不一致**：取消用例的前置条件在图与需求表中没有对应的支撑，检查时会被问“买家从哪里看到订单”。
2. **范围判断分歧**：若把“我的订单”当作独立用例，就超出教师给定的四项核心业务（B-01）；若不当作用例，就要说明它只是下单成功后的结果展示，不构成新的用户目标。

本稿建议：**不新增用例**，但在 FR-05 的成功后置条件中明确“系统向买家展示其订单标识与状态”，并说明本阶段不定义完整订单管理功能。这样既守住范围，又让取消用例的前置条件有依据。此事需组长确认后统一到需求表与用例图说明中。

### 12.4 仓库合规提醒（非本人主责，但影响提交）

以只读方式核查当前仓库公开属性，结果为 `private: false`，即**公开仓库**。与指导书第十节存在两处不一致：

1. 指导书要求“创建私有仓库”，并写明“不自行公开仓库”。公开仓库意味着任何人对需求草稿、组员账号、待确认问题都可读。
2. 指导书要求“公开材料不放完整学号、联系方式、密码或密钥”。本稿已只使用 GitHub 用户名，但仓库中其他材料（如工作表）若含实名或学号，公开状态下即构成泄露。

建议由组长确认是否为有意公开（部分课程允许，以课堂通知为准）；若不是，应在仓库 Settings 中改为 Private 后核实课程账号的 Collaborator 与 Projects 权限仍然有效。
